The verify-work-complete Stop hook: how it fires, and how agents react

A read of every gate fire in the last ~6 days of fleet sessions. Verdict up front: the hook is not "blind" about whether an open PR belongs to the current session — its PR attribution is precise. The real defect is the opposite: it over-fires and loops, re-blocking sessions that are legitimately waiting (background CI watch, downed reviewer, a human merge gate), because it has no memory of how often it already fired and doesn't recognize the very "watch-then-stop" pattern the repo's own rules prescribe. The fix is shipped (PR #158, live on claude 2.1.219) — but it exposes a deeper question worth more than the loop fix: the rule is watch then stop, and the real goal is agents that keep moving (§8, tracked in RUSH-2113).

1 · What the hook actually does

It is a Stop hook: exit 0 lets the agent stop, exit 2 blocks the stop and injects the stderr back as Stop hook feedback:. It runs five gates in order (all fail-open; stop_hook_active makes each fire at most once per stop attempt, but a fresh stop later re-runs the whole hook):

GateFires whenCited lines
open-PRSession created a PR (pr create tool_use paired to a tool_result URL) or worked one (gh pr merge/ready/rebase/close/reopen/edit, or gh pr view ≥2×) and it is still OPEN, and the final message has no handoff/blocked phrasing.48–207
swarmSession ran an edit-mode agents teams swarm and the final message claims done ("landed end-to-end", "all tracks merged").209–309
handbackWrote a runnable script to /tmp and told the user to run it.311–408
self-auditFinal message claims done / parks the next step ("want me to…", "on your go") — forces a goal-by-goal re-audit.410–722
deliveryverify-delivery-chain.py: a delivery stop with an unclosed Linear ticket / missing CHANGELOG.596–616

The open-PR gate has one narrow escape (lines 163–179): the final message must match a handoff phrase (handed off, owns (this|the) pr, is babysitting…) or contain blocked on and one of watcher | background watch | gh pr checks --watch | will merge on green | your touch id | biometric. This escape is the crux of the whole problem — see §5.

2 · Method & dataset

Every JSONL transcript modified in the last 6 days across all harnesses (1,635 files; 1,594 non-trivial). A genuine fire is a record with type:user, isMeta:true whose content string starts with Stop hook feedback:\n[…/00-agent-verify-work-complete.sh]: STOP GATE. This precise signature excludes meta-sessions that merely quote the hook's source or another transcript (an early false-positive that inflated counts 5×). For each fire I recorded the gate type, the cited PRs, the agent's next assistant message (its reaction), and — replicating the hook's own regex — whether each cited PR was created / worked / unattributed by that session.

4 · The "blind PR" theory — tested and disproved

The hypothesis was that the hook can't tell whether an open PR was opened by the current session. Two directions, both measured:

TestResult
Cited PRs that were actually created by the firing session382 / 382precise
Cited PRs merely worked or unattributed (false-positive attribution)0none
Sessions that created a PR but never fired the gate18check
…of those 18, PRs left OPEN (a true blind strand)016 merged · 1 closed · 1 test-fixture
Edit-mode swarm sessions with zero fires (teammate-PR blind spot)0 / 6all fired
Verdict. The gate is not blind about ownership. Every PR it cited was one the session genuinely opened, and no session slipped away leaving its own PR stranded. Several of the no-fire cases were agent-* teammate sessions that correctly drove their own PR to merge before stopping — the intended behavior.

5 · The real defect: the loop, and the too-narrow escape

The open-PR gate fired 434 times across the firing sessions — far more than the number of PRs — because it re-blocks the same session on every stop attempt while a PR is legitimately open (CI running, review pending). The repo's own rule is: after gh pr create, launch a background gh pr checks --watch and stop — the harness re-invokes you when CI settles. Agents do exactly that. But the gate's escape doesn't recognize it:

8%
of 434 open-PR reactions matched the gate's escape regex (would clear)
48%
described a live background watcher / "re-invokes me on green" but missed the escape regex → blocked anyway

The escape needs owns (this|the) pr or blocked on + a token. The natural, correct phrasing agents actually wrote — "the live watcher owns the next step and re-invokes me when CI settles" — matches neither, so honest agents loop, re-phrasing the same handoff 10–40 times until they stumble onto the magic words. Representative reactions, all blocked:

Live watcher `brulgiuml` (background `gh pr checks 1572 --watch`) owns the next action and will re-invoke me the moment CI settles — at which point I merge on green.
The live poller `b26l73hvl` owns the next step and will re-invoke me when prix-cloud posts its fresh verdict. That satisfies the gate (option 3, live process). Standing by.

Both are the right behavior. Both got blocked. The agent is caught between two rules — "watch-then-stop" vs "never stop with an open PR" — and the gate wins every round.

Second-order cost. Because the hook is stateless, it emits the identical "keep driving it" text on fire #1 and fire #38. It never notices it has already fired 20 times on the same PR, never changes tack, never says "you appear genuinely blocked — escalate." In one session (b0f09b87) the loop ran the agent straight into its Claude usage limit ("You've hit your session limit").

6 · Case studies

Five sessions read in full around every fire. Each ended on a real blocker the agent could not self-clear — yet the gate kept ordering it to "keep driving."

A · 24f4d5e9 — "Cursor agent parity" epic (RUSH-2079)

830 assistant turns · 38 open-PR fires · 204 min. Orchestrated 5 teammate PRs. The blocker: the repo's required automated reviewer prix-cloud was down fleet-wide (already filed as RUSH-2078). No non-author review ⇒ no merge ⇒ the gate blocked every stop for 3.4 hours. The agent even re-diagnosed the outage each loop:

`prix/code-reviewer` being down is already tracked as RUSH-2078 (Urgent). Adding my fresh evidence — the outage is wider than the 8 PRs it cites.

Lesson: a fleet-wide external blocker hit many sessions at once. The gate had zero cross-session awareness — it never told the agent "other sessions are stuck on the same reviewer; coordinate / escalate rather than re-assert."

B · e049f85d — daemon "no fallback token" invariant

1,055 turns · 19 fires · 550 min (9.2 h). PR #1583→#1658: CI fully green, an independent non-author reviewer returned Ready to merge — but the auto-mode classifier forbids self-merge and prix-cloud never posted. Midway the user put the session in plan mode, which mechanically forbids the push/merge the gate was demanding. It looped for 9 hours before finally texting Owner:

PR #1658 is handed off explicitly to Owner, who now owns the one remaining action: clicking Merge. This is not "awaiting review" — the blocker is the merge-rail approval gate.

Lesson: two blindnesses stacked — (1) the gate demanded a merge the session was in plan mode and could not perform; (2) a stateful hook should have said "escalate to the human" after ~3 fires, not after 9 hours and 19.

C · fe21bfab — cross-fleet sessions --active fix

1,324 turns · 26 fires · 627 min (10.5 h). Both root causes fixed and merged. Terminal state was a correct stop the gate kept fighting: an npm release needs the user's sign-off (outward-facing, hard to reverse).

I'm blocked on one thing that is genuinely yours: cutting an npm release … an outward-facing, hard-to-reverse action. Per the sign-off-before-publish rule, I won't publish autonomously.

Lesson: the agent obeyed a higher rule (get sign-off before an irreversible publish), and the gate treated that correct pause as abandonment.

D · b0f09b87 — command cleanup + fleet sync

370 turns · 16 fires · 387 min. Two hard walls: it hit the Claude usage limit mid-loop, and reconciling 3 divergent fleet boxes needs git reset/rebase — blocked by the git-guard (data-loss prevention).

I've exhausted the non-guarded tools. … clean resolution needs raw `git reset`/`rebase` (guarded on my shell).

Lesson: the only path forward was blocked by another guard. "Keep driving" is impossible; the gate should route to escalation, not repetition.

E · 819d1a19 — linear-cli comparison → build

890 turns · 17 fires (10 self-audit). On a repo with no CI and no automated reviewer, self-merge is blocked and there's nothing to wait on — yet the gate kept demanding the PR be driven, and the self-audit gate kept re-demanding a goal ledger the agent had already produced.

Not stopping dead — the PR is actively driven. … `prix-cloud`: not yet posted … Live watcher `b2op4gpj0` is running now.

Lesson: on a repo with no reviewer configured, the "get a non-author review then merge" path can never complete — the gate needs to recognize that and allow an explicit human handoff sooner.

7 · Proposed improvements

Direct response to the failure modes above, folding in your ideas (stateful de-escalation, remind agents of their sleep/monitor tools, escalate to you / broadcast / coordinate with sibling agents).

Fix 1 — Make the hook STATEFUL (highest impact)

Count how many times this same gate already fired in this transcript (scan for prior Stop hook feedback: … STOP GATE (<type>)). Change the message by fire count:

  • Fire 1–2: current "keep driving" text.
  • Fire 3+ on the same thing: switch to a de-escalation message: "This gate has fired N× on the same item — you are not abandoning it, you are blocked. Stop re-asserting. Do ONE of: (a) if a live background watcher / monitor already owns the next step, that IS a valid stop — name it and stop; (b) escalate out-of-band to Owner (rush message send) if the blocker is a human gate (merge auth, release sign-off, plan mode); (c) broadcast + coordinate: agents feed post and agents sessions --active to find sibling sessions stuck on the same wall (e.g. a downed reviewer); (d) set a ScheduleWakeup/monitor and stop."

Kills the 22 sessions that looped ≥10× and the quota burn.

Fix 2 — Recognize the native wait tools & live watcher as a valid stop

  • Detect an actual live background task in the transcript since the PR was created — a Bash run_in_background gh pr checks --watch, or a ScheduleWakeup/Monitor tool_use — and treat it as a legitimate handoff (the watcher owns the next step).
  • Broaden the escape regex to accept the natural phrasing agents actually write: (watcher|poll|reviewer) … (owns|driving|re-invoke|will merge on green), re-invokes me when — without requiring the literal blocked on.
  • Keep the anti-abandonment core: only clear when there is evidence of a real live process (a tool_use) or an explicitly named owner — not just any mention of "watch".

Targets the 48% of open-PR blocks that were correct behavior mis-scored as abandonment.

Fix 3 — Context awareness the gate currently lacks

  • Plan mode: if the session is in plan mode it physically cannot push/merge — don't demand it drive the PR (case B).
  • Reviewer / CI down: if the agent names the automated reviewer or CI as down/absent (or no reviewer is configured on the repo), accept an explicit human handoff without the narrow token set (cases A, E).
  • Irreversible-action pauses: a stated "won't publish/release without your sign-off" is a correct stop, not abandonment (case C).
Shipped. All three fixes merged in PR #158 and are live on claude 2.1.219 (verified on the installed hook). 89/89 tests. A non-author review caught a real over-match bug (no ci failures clearing the gate) — fixed and pinned before merge.

8 · The deeper question — keep moving, don't just stop

The fix above stops the looping. But it exposes a design flaw the shipped change only half-solves, and it's the more important one: the repo rule is "watch, then STOP" — and the real goal is agents that keep MOVING. Agents stop too early. Teaching the hook to recognize a watcher made honest agents stop cleanly, but "a watcher exists" became blanket permission to stop — which is the wrong lesson.

A live watcher owning PR-A means you don't have to babysit PR-A — it does not mean the task is over. If another PR is open, a task is unfinished, or the queue has more, the agent should advance the next thing, not stop. "Watch then stop" should become "watch, then keep moving; stop only when nothing else is advanceable."

Two situations the current hook (and the shipped fix) still can't tell apart:

SituationRight behaviorCurrent
Watcher owns PR-A, nothing else remainsStop — efficient (harness re-invokes on CI settle)correct
Watcher owns PR-A, but PR-B open / tasks left / queue has moreKeep moving to the next thingstops too early
