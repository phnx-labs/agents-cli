01What a routine does today

A routine is a YAML file in ~/.agents/routines/. A background daemon on each device parses its cron expression with croner, and at fire time spawns an agent, a workflow, or a plain shell command, capturing the output into a run record under ~/.agents/.history/runs/<name>/<runId>/.

Two fields decide where it happens. devices: is the firing allowlist — which daemon may fire it at all; each listed device fires independently. hostStrategy: is placement — where the job body executes once fired. They are different questions, and conflating them is a recurring source of confusion.

The whole design rests on one assumption that turns out to be load-bearing: the daemon is running when the clock strikes. Everything below follows from where that assumption breaks.

04Why the reporting lies

Four independent defects all present as the same symptom — red where there should be green, or green where there should be alarm.

  • Wrong device. Status was resolved from the local runs dir even for routines pinned elsewhere. fixed
  • Wrong epoch. Overdue looks back a fixed week, ignoring when the routine came to exist on that device.
  • No miss state. A fire that never happened writes nothing, so the previous run's status persists indefinitely.
  • No failure reason. A quota kill records failed with an empty errorMessage.

05What I propose, and why

Phase 1 — make every failure state its reason

Extend the failure classifier beside the existing isAuthFailureFromLog / authFailureReason in runner.ts to recognise a 429 / rate_limit / "weekly limit" result and record a structured reason. Reuse the rate_limited vocabulary already in usage.ts rather than inventing a second one. Notify once per quota window, not per failed run.

Why: a run that records failed with no reason is indistinguishable from a code bug, so you cannot triage without SSH-ing to the box and reading raw stdout — which is exactly what today cost. Benefit: the menu bar already renders failureReason, so it inherits this for free.

Phase 2 — make "overdue" honest

Give detectOverdueJobs an effective-start floor: the later of the routine's creation/last-pin time and the device's own scheduler start. Stamp createdAt / pinnedAt in writeJob, which already stamps actor.

Why: this is the blocker for auto-catchup. Benefit: a young routine reads "not yet due" instead of "overdue", and auto-catchup stops being a footgun that fires every new routine on creation.

Phase 3 — remove the phantom device

Either make worker an alias that normalizeHost resolves to yosemite-s1, or fail loudly when a pin resolves to no live machine. A routine pinned to a name no machine answers to must be marked in the listing, never silently inert.

Why: a pin that matches nothing is the most confusing possible failure — the routine looks configured and enabled, and simply never happens.

Phase 4 — keep the daemon supervised

Teach agents doctor to flag a service-manager unit that is enabled but failing. NRestarts in the thousands with the daemon alive only as a detached process is precisely the state that went unnoticed for weeks.

Benefit: the daemon survives reboots, which it did not before today.

Phase 5 — finish what is in flight

Merge #1773 once Phase 2 lands, then re-triage the remaining failures with the reason field actually populated. Several may turn out to be Phase 1's quota issue wearing a different mask.
