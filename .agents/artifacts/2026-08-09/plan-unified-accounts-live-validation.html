Purpose

When a user names a native login, the same logical account name should appear anywhere that identity is selected or displayed. When a user adds a provider credential, several custom harnesses should be able to reference that account without copying or owning its secret. An explicit account must either launch exactly that authorization identity on the execution device or fail before spawning.

The current release does only the first slice. A label stores one harness id plus an identity fingerprint, Cursor OAuth is device-global, profile YAML owns provider auth, and the broader API-key implementation remains on a conflicting PR.

Acceptance boundary: success means real installed runs through at least two independent provider keys, a real Claude setup-token path, a shared account used by two harnesses, and a remote missing-account failure that launches nothing.

Credential kinds delivered as real paths, not placeholders:

  • managed-login: native harness identity discovered from a live version home. Claude headless execution continues resolving that identity's existing setup-token where present.
  • api-key: account-owned secret reference with provider/host injection. Cursor and OpenRouter are the mandatory live adapters; all built-in preset providers receive an adapter or an explicit host-managed declaration.
  • setup-token and bearer-token: account-owned token references for providers whose adapter declares the method. Claude setup-token is validated and injected only on the non-interactive path; explicit caller overrides retain the existing merge precedence.
  • OAuth stays provider/harness-managed unless an adapter owns a complete login and refresh lifecycle. No generic OAuth record is advertised without that real path.

Public Interface

The final commands retain shipped managed-login naming and add provider accounts plus harness references:

agents accounts
agents accounts name work --from claude@2.1.220
agents accounts add openrouter-work --provider openrouter --auth api-key
agents accounts add cursor-work --provider cursor --auth api-key --from-secrets cursor:CURSOR_API_KEY
agents accounts add claude-worker --provider anthropic --auth setup-token --from-secrets auth:CLAUDE_CODE_OAUTH_TOKEN_...
agents accounts set-key openrouter-work [--from-secrets bundle:key]
agents accounts inspect openrouter-work [--json]
agents accounts rename <old> <new>
agents accounts remove <name>

agents harness add deepseek --preset deepseek --account openrouter-work
agents harness edit deepseek --account openrouter-staging
agents harness view deepseek [--json]

agents run deepseek --account openrouter-work "Reply with exactly ACCOUNT_OK"
agents run cursor --account cursor-work "Reply with exactly CURSOR_ACCOUNT_OK"

--auth-provider and profile-owned auth.envVar/keychainItem are migrated and removed from the runtime. Stale automation receives an explicit replacement command; there is no compatibility fallback. An explicit --account overrides a harness default, while an explicit --env remains the final per-run override.

Validation

Implementation verification runs in this order:

  1. Focused source tests cover registry migration, provider completeness, secret cleanup, profile references, merge precedence, rotation, surfaces, and every local/remote execution boundary. Tests use real temporary files and the real secrets backend seam; no network path is mocked.
  2. Run the canonical build and laptop-safe full suite.
  3. Install the built CLI through scripts/install.sh; quote the installed dev version and command help.
  4. Snapshot the existing account/profile metadata, trigger the real migration, and compare account ids, harness references, and secret presence without revealing values.
  5. Run two existing OpenRouter keys as two named accounts and prove distinct selection. Bind one account to two harnesses and prove both runs return their exact tokens.
  6. Run a real named Claude managed-login account headlessly and verify the selected setup-token path; run the interactive path separately to prove it retains the native login.
  7. Create/import a Cursor user API key when an authenticated dashboard session permits it, validate it through the installed Cursor CLI, and record the exact response. If Cursor account creation is human-login gated after all configured browser sessions are tried, the report marks only that adapter unverified; OpenRouter still proves generic multi-account behavior.
  8. Dispatch to a device that has synced metadata but lacks the secret. Assert a named pre-spawn failure and verify no session/process was created.
  9. Open the PR with actual run assets, obtain non-author review, fix CI/review, merge on green, then confirm the commits are on origin/main. The release train owns npm publication.
