Interesting patterns

Counting is a different hot path

The origin-partitioned 100-session count p95 is 3.18 ms because it aggregates persisted occurrences without hydrating calls. At the 4,756-session metadata scope it reaches 13.05 ms while grouping both totals and coverage by true origin machine.

Metadata scope growth stays bounded here

Moving from 100 to 4,756 session IDs adds 4.37 ms to one-clause p95 and 3.44 ms to positive two-call p95. The query sends the scope to SQLite once with json_each(?), instead of issuing one query per 300 IDs.

Two positive clauses do not double latency

The one-clause query returns 16 sessions and the two-distinct-git-call query returns 17. The latter's p95 is 10.16 ms versus 8.80 ms for one clause; indexed prefilters shrink the candidate set before distinct-call assignment.

Program use is heavily concentrated

Within the origin partition of the 100-session sample, 1,075 static git sites live in 554 calls across 18 sessions: 1.94 sites per containing call and 59.7 sites per containing session.

WAL is not permanent overhead

The clean historical backfill peaked at a 36.2 MB WAL, then checkpointed to zero. It occupied 25.6 MB of database pages but did not grow the 912 MB file because existing free pages absorbed every new row.

Queries are read-only

After the checkpoint, 180 measured tool-query executions changed both the DB and WAL by exactly zero bytes. Parsing and writes occur during normal incremental scanning or explicit backfill, never during lookup.

Coverage caveat. The representative sample produced current ledgers for 97 source files and one explicit index-limit row. No files remained queued, but coverage is marked incomplete and the count is a lower bound. The 4,756-session figures vary the metadata ID scope over the same 100-session indexed snapshot; they do not claim that all 4,756 transcripts were backfilled.
