- **`agents repo sync <alias>` is a new git-level sync verb for a single DotAgents repo.** The old `agents sync <repo>` umbrella syncs resources (skills, hooks, memory, …) from the repo's files into each agent's home dir; `agents repo sync` only does the git pull/push — the same step `agents sync` does first, now accessible on its own. Alias semantics: `system` is pull-only (the system repo is a read-only mirror); `user` and any registered extra also push. The command mirrors the existing `repos pull` / `repos push` pair's alias grammar but runs them as one round-trip. Source: `apps/cli/src/commands/repo.ts`.

- **`agents hooks sync`, `agents skills sync`, and `agents commands sync` — dead error stubs removed.** These hidden subcommands existed solely to print `"agents X sync" is gone.` and exit 1. They pre-dated auto-sync on launch and had no callers; removing them cleans the command surface without any behavior change (auto-sync on launch remains). Source: `apps/cli/src/commands/hooks.ts`, `apps/cli/src/commands/skills.ts`, `apps/cli/src/commands/commands.ts`.

- **`agents plugins sync`, `agents memory sync`, and `agents mcp register` are deprecated** — each now prints a one-line warning and the `agents sync --plugin`/`--memory`/`--mcp` replacement, then runs the existing logic unchanged. They are hidden from `--help` but remain functional for one release so scripts and muscle-memory don't break cold. Source: `apps/cli/src/commands/plugins.ts`, `apps/cli/src/commands/memory.ts`, `apps/cli/src/commands/mcp.ts`.

- **Daemon housekeeping is daemon-core timers again, not routines — the "maintenance-routine" layer is removed (RUSH-2495).** RUSH-2353 had turned the daemon's own housekeeping (`watchdog`, `device-probe`, `tmux-reconcile`, `launch-health`, `session-cache-warm`, `auto-dispatch`) into scheduler routines, and RUSH-2465 (merged but unshipped) moved their definitions into daemon code as built-in routines injected at the bottom of `listJobs()`. A daemon's own housekeeping does not belong in the routines surface — it cluttered `agents routines list` with entries a user can neither meaningfully edit nor should, and carried a `__daemon-tick` entrypoint, a built-in-routine registry, and per-job `builtin` provenance plumbing just to hide them again. This is a hard cut: `watchdog` and `device-probe` are back to plain `setInterval` timers the daemon holds directly (`apps/cli/src/lib/daemon.ts`), gated exactly as before (`watchdog.enabled` config); `tmux-reconcile`, `launch-health`, and `auto-dispatch` are deleted outright along with the `auto-dispatch*.ts` modules; `session-cache-warm` is dropped because `agents sessions --active` already self-refreshes on a 15s TTL. `usage-refresh` and `fleet-cache-warm` were already `account-state-service` timers and are untouched. `agents routines list` no longer shows any housekeeping entries. The `builtin-routines.ts` registry, the `__daemon-tick` entrypoint, `DAEMON_TICKS`, and the `JobConfig.builtin` field are gone. Source: `apps/cli/src/lib/daemon.ts`, `apps/cli/src/lib/daemon-ticks.ts`, `apps/cli/src/lib/routines.ts`, `apps/cli/src/lib/overdue.ts`, `apps/cli/src/lib/migrate.ts`, `apps/cli/src/index.ts`. Paired with the `phnx-labs/.agents-system` change that removes the routine YAMLs.
- **A dismissed ("Ignored") device is never re-surfaced by the daemon device probe (RUSH-2495).** After a user pressed "Ignore" on the menu-bar "NEW DEVICES" prompt, the probe could re-surface that device: the probe computed its pending set before the dismissal (`addIgnored`) landed, then the sentinel writer (`reconcilePendingSentinels`) wrote a fresh sentinel for it and the menu bar showed it again. The sentinel writer — the single choke point every discovery path (daemon probe and `agents sync`) flows through — now re-subtracts the persisted ignore-list itself, so a device on the ignore-list is never written regardless of what the caller passed. Source: `apps/cli/src/lib/devices/pending.ts`.
- **`agents sync <repo>` no longer strands a merged change behind unrelated local edits.** A dirty working tree used to fail the sync outright, so one modified `agents.yaml` or a session's scratch file froze that box's layer at whatever commit it was on — silently, with nothing reporting it. Measured 2026-08-10: a merged fix could not reach three of three boxes, each blocked by files the incoming commits never touched. Now a dirty tree fast-forwards instead of rebasing, but only when that is provably safe: no local commits ahead of upstream, and no incoming path colliding with a dirty one. Otherwise it still refuses, and the message names the colliding paths (or the local commits) instead of just "uncommitted changes". A clean tree still rebases exactly as before. The rule lives in one place (`dirtyTreeRefusal`) that **both** `syncRepoGit` and `pullRepo` call, so `agents sync <repo>` and the bare `agents sync` umbrella — which reaches the user repo and `.system` through `pullRepo` — cannot answer the same question differently. `--ff-only` is the safe primitive here — it cannot rewrite local commits, and git aborts rather than overwrite a modified file, so the path check is a second guard rather than the only one.

- **A unified `agents config` namespace replaces the scattered configuration surface.** The CLI previously spread run defaults (`agents defaults run`), model-tier overrides (`agents models tier`), interactive host preference (`agents devices configure` / `agents devices set-interactive`), and the default browser profile (`agents browser profiles set-default`) across unrelated command trees. The new `agents config` command exposes a single `agent@version` keyed grammar:
  - `agents config list` prints every persisted key/value.
  - `agents config get <key>` reads one value.
  - `agents config set <key> <value>` writes one value.
  - `agents config unset <key>` removes one value.
  Supported keys: `run.<agent@version>.model`, `run.<agent@version>.mode`, `run.<agent@version>.effort`, `run.<agent@version>.tier.<cheap|default|best|ultra>`, `interactive.host`, `browser.profile`, and `devices.<name>.max-agents` / `scheduler` / `daemon` / `watchdog` / `browser.remote-control` / `notes` / `browser.profile`. The `@version` component accepts `*` for version-wide defaults and `latest` for the newest installed version. `interactive.host` is a fleet-wide user-level preference stored in central `~/.agents/agents.yaml`; it is not a per-device key. Storage is unchanged — `agents config` is a facade over the existing `run.defaults`, `model.tiers`, `config.*`, device config, and meta defaults — so mixed-version machines and the fleet stay compatible without migration. The old commands still work but emit a deprecation warning pointing to `agents config`. Teams remain intentionally out of scope for persistent config because teams are temporary. Source: `apps/cli/src/commands/config.ts`, `apps/cli/src/lib/config-keys.ts`, `apps/cli/src/lib/run-defaults.ts`, `apps/cli/src/lib/model-tier-overrides.ts`, `apps/cli/src/commands/defaults.ts`, `apps/cli/src/commands/models.ts`, `apps/cli/src/commands/ssh.ts`, `apps/cli/src/commands/browser.ts`.

- **`agents devices config <name> --inherited` shows user-level config that applies to a device.** Device config views (`agents devices config`, alias for `configure`) only display device-scope keys by default. With `--inherited` they also render user-level keys such as `interactive.host` under a separate "Inherited from ~/.agents/agents.yaml" section, so operators can see fleet-wide settings in the per-device context without mistaking them for device-local values. Source: `apps/cli/src/commands/ssh.ts`, `apps/cli/src/lib/device-config.ts`.

- **Monitors gain a built-in/system layer, so a monitor can ship with the CLI (RUSH-2472).** Monitors previously resolved only the user dir (`~/.agents/monitors/`), so no built-in monitor could ship the way routines already ship built-ins from `~/.agents/.system/routines/`. `listMonitors()` / `readMonitor()` / `getMonitorPath()` now union the user dir over the system dir (`~/.agents/.system/monitors/`, shipped via `gh:phnx-labs/.agents-system`), with the user layer shadowing a system built-in of the same name — mirroring the routines project/user/system resolution. A system built-in with no `enabled:` field is **opt-in**: it stays disabled until the user enables it, matching how routines treat a fresh built-in. Enable, edit, and delete always target the user dir — the system mirror is pull-only, and enabling a built-in materializes a user copy — so the daemon's `MonitorEngine` (which fires `listMonitors().filter((m) => m.enabled && ...)`) picks up enabled system monitors with no further change. New env overrides `AGENTS_MONITORS_DIR` / `AGENTS_SYSTEM_MONITORS_DIR` mirror the routines pair. Source: `apps/cli/src/lib/state.ts`, `apps/cli/src/lib/monitors/config.ts`.

- **The `agents pr` command group is removed; merge-on-green belongs to a built-in monitor (RUSH-2472).** `agents pr` / `agents pr land` was a bespoke command that duplicated, as a one-off CLI surface, the watcher shape monitors already own — a source polled on an interval, a condition, an action — and it carried its own detached-lander process/state machinery (`~/.agents/.history/pr-land/`) as a second scheduler beside the daemon. With monitors now able to ship built-ins from the system layer, merge-on-green is a monitor rather than a command, so `agents pr` and its `--detach` lander are gone. Two things are deliberately kept: `lib/teams/pr-watch.ts`, the reusable CI/review polling the monitor will reuse, and the headless-exit warning that fires when a run leaves its branch on an OPEN PR — that warning no longer names a removed command and instead says to merge the PR or set up a merge-on-green monitor. Source: `apps/cli/src/commands/pr.ts` (deleted), `apps/cli/src/lib/pr-land-detach.ts`, `apps/cli/src/lib/startup/command-registry.ts`, `apps/cli/src/commands/exec.ts`.
