User stories that stop product regressions

Agents write the code. Humans orchestrate with HTML plans and tests — and still ship product regressions. The hole is not “more technical design.” It is missing approved, test-mapped user outcomes and a short must-not-break list.

01 Diagnosis — how we ship today

Real plans in this fleet (plan-agents-monitors.html, plan-agent-login-status.html) look like: Why → Design/API → Files → Verification of the new surface. That is excellent implementation design. Product regressions are failures of what must stay true for users.

You are not “speccing” when an agent shows a plan or a mockup. You are product-speccing when behavior is written as Given/When/Then, you accept it, and a proof command (or test) can fail if it is wrong.

02 Bad vs good user stories

Bad — common agent filler

Better session visibility

As a user I want better session visibility so I can be more productive.

  • No role that does a real job
  • No command or UI surface
  • No observable Then
  • Agent invents UI
Good — product acceptance

See host on live sessions

As an operator on a busy laptop, I want agents sessions --active to show which host each live agent is on, so I know where to attach without guessing.

  • Role + concrete surface
  • Independent test: two hosts, one command
  • Scenarios can map to tests
  • Must-not-break JSON for Factory

03 Three Product cards (copy these)

Card A · sessions

P1 — See where live agents run

As an operator on a busy laptop, I want agents sessions --active to show which host each live agent is on, so I know where to attach without guessing.

Independent test: one local + one remote live agent; one command shows distinct hosts.

  1. Given Claude live on workstation and Codex live on release-host When I run agents sessions --active Then each row shows the correct host (not blank / not swapped).
  2. Given no live agents When I run agents sessions --active Then exit 0 and empty state, not an error.
  3. Given the same live set When I run agents sessions --active --json Then each object includes a stable host field Factory Floor can parse.

Must not break: preview one-liner · empty vs error exit codes · JSON renames without COMPAT.

agents sessions --active
agents sessions --active --json
Card B · run preflight

P1 — Warn before burning a dead account

As an operator, I want a clear “logged out” warning before a headless run waits on a 401, so I do not waste minutes.

  1. Given Claude not authenticated on this version home When I agents run claude "hi" Then I see a warn naming the agent and how to log in (policy stated: warn+continue or hard-stop).
  2. Given account healthy When I run the same command Then no false logged-out warning.

Must not break: doctor, view, and menubar use the same probe.

# unhealthy home → warn; healthy home → silent
agents run claude "hi"
Card C · teams

P1 — Parallel tracks do not thrash main

As an operator, I want each teammate in its own worktree with clear Owns, so parallel implement does not corrupt a shared checkout.

  1. Given a team with two edit-mode teammates and --enable-worktrees When both start Then each writes only under its worktree; main stays clean of teammate edits.
  2. Given teammate A Owns src/auth/* When A is briefed Then the brief forbids src/ui/*.

Must not break: single-agent agents run without teams; default branch untouched.

git -C "$REPO" status --short   # main clean of teammate edits
ls .agents/worktrees/           # teammate worktrees present

04 Must-not-break pack (paste into every user-visible PR)

Regression pack · example

After implementing the new path, still prove these (adapt per surface):

  • --json fields used by Factory / scripts still present
  • Exit codes: empty success vs real error still distinct
  • Defaults unchanged unless the Product card says so
  • Docs / CHANGELOG for user-visible flag or behavior
  • Quoted output of proof commands in the PR body (F3)

05 The loop that closes the hole

Figure — Product acceptance sits between plan and implement. F3 quotes proof commands from the card.

Feed the factory with outcomes, not vibes. Short Product cards (1–3 stories, 3–7 scenarios, must-not-break, proof commands) are enough. Full OpenSpec/BMAD is optional; this is the peer to your HTML plans.
