# Proposed post-change contract

PHNX-3940. Normative language below describes the target, not today's guarantees.

1. An account ID is independent of release, device and display name. Account labels are scoped by harness. An account can have native and supported automation credential variants without a second user-visible identity.
2. A device-local Home record has an immutable ID, harness, exact native path, optional account ID, and managed/adopted/preserved state. Existing paths remain unchanged during migration. No home data is deleted by release retention.
3. A managed Release record is keyed by harness, OS, architecture and vendor release, includes validated entrypoint and integrity evidence, and is immutable after publication. A device has one current release pointer per managed harness; extra releases require a stated pin, running lease, rollback window, or unresolved ownership.
4. Every launch resolves one selection before spawn: stable account → device-local home; explicit pin or harness current → executable; device role plus vendor-supported invocation surface → credential. Authentication checks, usage attribution, executable execution and resume MUST reference that same selection. A failed identity check cannot silently try a different account.
5. A new release MUST NOT change account-home paths or credential contents, log users out, or mutate running processes. A new account MUST NOT install a duplicate package when its required release is already available. The zero-account state may retain one installed current executable; no-account does not mean no-harness.
6. Auto-update defaults on for supported managed harnesses. Global off overrides harness on. Explicit release pins remain pinned. One scheduler and one per-harness transaction owner govern manual/background updates, migration and retention. A failed probe leaves current unchanged; cancellation before publication leaves no half-live selection.
7. New launches can select the newly published immutable release while old launches retain their lease, only where the adapter has proven mixed-version native-home compatibility. Otherwise a busy home's next selection is deferred until idle; its native data is never migrated under a running process. A leased release cannot be removed. An active home is not a reason to download the same executable again. Unknown process attribution means retain, not delete.
8. Migration is idempotent and metadata-only with a resumable journal and old-writer/schema fence. Explicit bindings/defaults win; ambiguous unbound homes require selection. Existing labels, pending connect attempts, pins and session references survive. Source directories are never merged on email alone.
9. Native credentials are local to a device. Personal/desktop native-account runs MUST NOT receive portable worker credentials through any later environment layer, vendor-loaded user/project/managed settings, credential helper/profile, provider selector or CLI override. Preserve settings and reject effective credential conflicts or unknown precedence; a preflight environment/file check alone cannot guarantee post-load enforcement. Missing native login yields reconnect-needed, never a token or billing fallback. Supported worker tokens are delivered only to explicitly enrolled trusted targets.
10. Credential delivery is revisioned per account/kind and acknowledges the exact durable revision. A peer with an older existing bundle is stale, not ready. Revocations/tombstones outrank old seeds; an offline peer remains pending and may retain a still-valid credential until provider revocation/expiry. No promise of instantaneous remote erasure is made.
11. Claude token minting uses the selected account identity. Codex workspace tokens require actual permission and supported non-interactive use. Personal Pro and unsupported surfaces use independent per-worker native login where supported. No universal one-year Codex capability or silent API billing fallback is claimed.
12. UI state distinguishes policy, selected/current/target releases, daemon liveness, updater last successful pass, local credential presence, dated live identity verification, and peer synchronization revision. None substitutes for another. Health/usage caches expose age and source; stale or missing is unknown, not connected/ready.
13. `agents view <harness>` and `agents accounts` are account-first. `--versions` shows actual shared releases with retention reasons, and a separately labeled legacy-alias/home mapping. Legacy JSON remains available additively during migration; new explicit fields carry a schema version. Display commands are read-only.
14. Native config/skills/hooks projection enumerates homes, not releases. Installing a new shared release does not replicate account configuration. Session metadata records resolved account ID, home ID and release key separately; resume cannot infer the account from the executable's version.
15. Cleanup previews classify exact manager-owned package paths separately from native homes and Agents CLI installs. Legacy removal needs explicit approval. New cache retention protects current, pinned, active and rollback references; it never guesses ownership or follows an escaping symlink.
16. Mixed fleet versions negotiate capability/schema before enrollment or new-layout execution. A worker below the minimum supported CLI reports upgrade-required and retains its existing state; it is not provisioned or marked ready by newer metadata it cannot execute. Activation requires proof that old entrypoints are upgraded or reliably blocked; an unaware old executable cannot be assumed to honor a new marker.

Delivery proof belongs to the installed artifact, not a merge. See [tasks](tasks.md) and the [rendered plan](plan.html) for gates.
