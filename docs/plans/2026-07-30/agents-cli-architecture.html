How agents-cli runs, watches, and shows agents across a fleet

A plain-language tour of the parts that matter for scale — every claim points at the exact file and line: the data structures, session ids per harness, where things are stored, what actually runs on the common commands, and teams / running agents on other machines. Then the slow spots, and the one change that fixes most of them.

repo agents-cli @ dfe9f011 apps cli · factory pkg session-tracker every claim has a file:line read from source, not guessed

agents-cli is two separate programs, not one: the agents command-line tool (apps/cli) and the Factory VS Code extension (apps/factory). They share no memory and no code — the extension launches the CLI as a subprocess and parses its JSON output. A third piece, the hook, is a shell script the CLI installs into each agent's own config; it runs inside the agent process. This doc is about the CLI.

  • the event + activity logs; agents feed

01

Session identity: who assigns the id, who records it, when CLI HOOK EXT

"Session" means two things. A transcript (the conversation on disk — everything from §2 on) and an identity (which running process is which session). This section is the identity half, because it's the part people find confusing — three different things can write "pid → session id", and which one fires depends on the harness and how the agent was launched.

Start here: an agent is a process, and we need to name it

An agent is one OS process with a pid. To say "this terminal is running session 4d…" something has to map that pid to a session id, and store it in a file named after the pid (never the database — a pid is an OS-recycled number, so a saved pid 1234 → session-abc row becomes a lie the moment 1234 is reused; a file named 1234.json is overwritten by the next agent and deleted when the pid dies — reader.ts:113). The twist: the id doesn't come from one place. Depending on the harness, either we pick it, or the agent picks it and we find out later.

Three writers put "pid → id" on disk — and they fire at different moments

  • ① ag run CLI — for Claude it generates the id (a UUID) and passes --session-id, which Claude uses to create the session with exactly that id (exec.ts:1276, :821). So the id is known before the process runs → written immediately, exact (exec.ts:1193).
  • ② the shim CLI — the transparent wrapper (execShimPassthrough, exec.ts:976) forwards raw args untouched. It doesn't invent an id, but if a caller (Claude Code background jobs, an IDE) passed --session-id, it records that exact id via extractSessionIdArg (exec.ts:1014). Vital on Windows, where there's no lsof to recover a process's cwd afterwards.
  • ③ the SessionStart hook HOOK — a polyglot shell hook installed in each agent's own config. It reads the id from the agent's own payload and writes the extension's file, after the agent boots. It's the only writer that sees agents we never launched (you typing claude in a terminal) — but only for harnesses that expose a hook, and only after a short lag (trackSpawn polls up to 5s — index.ts:40).

Who assigns the id — it differs per harness

This is the crux of "why isn't it uniform." The dividing line is who names the session:

So Claude is the only harness where the id is ours and known up front. For everyone else the agent owns the id and we discover it — via its hook (if it has one) or by reading it out of the transcript later. That's why the pid-registry's sessionId is often empty for non-Claude at launch: the entry still records pid + cwd + agent so --active can correlate by folder until the real id shows up.

Can we collapse to one? — yes

Neither file subsumes the other today (immediate-but-our-launches-only vs delayed-but-any-launch), which is why both exist. But they hold the same data and can be merged: one pid → id file, two writers — the launcher writes it at spawn (pid + cwd + any id it knows), the hook fills in the authoritative id once the agent emits it. The join already exists — the hook records terminal_id / launch_id from env (AGENT_TERMINAL_ID set by the extension, AGENT_LAUNCH_ID by the launcher). Both the CLI and the extension then read the one file. This is the real "one file, two writers" fix — not "put it in the database."

In teams and headless runs

  • Teams · Claude teammate — the team generates one UUID as the teammate's agentId and passes it as --session-id, so the agent_id and the Claude session id are the same string (one identity for the teammate) — agents.ts:1610, :2288.
  • Teams · non-Claude teammate — "other agents don't expose a launch-time" id (agents.ts:1668), so the agentId and the session id stay separate until ③ / the file reveals it.
  • Teams · remote teammate — the teammate runs agents run … over SSH, so its pid-registry entry lives on the remote box. The supervisor doesn't use it — it tracks completion via the .log/.exit files (§6C, §10).
  • Headless (ag run --headless) — same run path as interactive: still writes the pid-registry (exec.ts:1373), Claude still gets a generated --session-id, and ③ still fires if the harness supports it. Only the TTY is missing.

The other meaning: a session's transcript

Everything from §2 on is about the other "session" — the conversation on disk (one file or DB row per session): its id format, indexing, storage, and reading.

04

Where each thing is stored CLI EXT

Five different places, each chosen for three reasons: how long it must live, who writes it, and how it's read back. The shape of each box tells you the kind of store; almost everything here is CLI-owned — the only extension-specific store is terminals/sessions/ (the extension's pid→id, §1).

05

Listing sessions reads a SQLite index — and only re-reads files that changed CLI

A fair worry: agents write to their transcript fast, so does listing them re-read everything each time? No.

  • A table called scan_ledger (db.ts:103) remembers each file's size and modified-time. On a scan, a file is only re-read if those changed. agents sessions then reads rows from the database, not the raw files.
  • The scanners (discover.ts:2227, :2458) read a changed file line by line and pull out metadata only (topic, counts, PR url) — never the full conversation.
So, to be exact

Listing and searching = a database read, and only changed files get re-read into it. The only time the whole conversation is parsed is when you open one specific session to read it (§6, walkthrough B).

06

Three walkthroughs: what actually runs CLI

All three are CLI commands (the extension just calls the first one). The chip on the right answers "does it re-parse, or just read the database?"

  • A (--active) re-reads the tail of every live session on each call — active.ts:389 readSessionTailWithRaw, state from state.ts, tokens/sec from throughput.ts. Other machines: one SSH per peer running the same command with --local.
  • B (one session) looks the id up in the DB for the file path, then fully parses that file — sessions.ts:1634 parseSession → render.ts. Reading the same session twice parses it twice.
  • C (teammate done) each teammate writes its exit code to a .exit file; the supervisor reads it (locally via reapProcess, remotely by tailing the log + reading the remote .exit, batched one SSH per host), flips the status, then startReady launches whatever was waiting on it — agents.ts:180, :861, teams.ts:361.
07

The Factory extension asks the CLI every 3 seconds — nothing pushes to it EXT

This is the extension's behavior — but note the root cause is the CLI's: sessions --active recomputes state on every call (§6A), so any poller pays for it. The extension just multiplies that cost. Fix it at the CLI and every consumer benefits.

// apps/factory/src/vscode/remoteSessions.vscode.ts
runs agents sessions --active --json as a subprocess  // :211
every ~3 seconds (:55) · three modes: this machine only · every machine over SSH · one machine on demand (:281)
// then reshapes the JSON and hands it to the React UI
The expensive path

Every 3 seconds, for each machine, the extension starts a whole new agents process, which does the scan and re-parses the tails (walkthrough A), prints JSON, and exits. That work is thrown away and redone 3 seconds later. It never reads the event logs — the ready-made stream of "what happened" (§9) is sitting right there, unused by the live view.

08

One file-watcher for the whole machine EXT

This one is entirely in the extension (the CLI has no resident watcher — it scans on demand, §5). Inside Factory, one process is elected "leader" and watches all the session folders so each editor window doesn't have to.

  • monitor/sessionWatcher.ts:70 sets up one recursive watch per session folder, waits 300ms after a change, reads only the first 100 lines to figure out which window a new file belongs to, and tells the windows.
  • It asks the CLI where the folders are — agents sessions --roots --json (sessionParse.ts:202) — so it stays in sync when a harness moves its files.

events vs activity: two logs, one shape, no database CLI

You asked why both exist. They're the same idea — a log of "X happened at time T" — split only by who writes it and how often.

What it recordsthings the tool does: ran a command, made a team, fetched a secretthings the agent does: made a plan, opened a PR, edited a file
Whereone shared file ~/.agents/events.jsonlone file per session activity/<id>.jsonl
How oftenrarely (low volume)constantly (high volume)
Lockinglocked — many processes share one fileno lock — each session owns its own file
Written byemit() in the CLI — events.ts:464the agent's hook (and appendActivityEvent) — activity.ts:108

So: activity is events. Same record names (plan.created, pr.opened, file.edited), read back together by one function, event-stream.ts:57 readUnifiedEvents. The split exists for one reason: if every high-frequency agent event also went into the single locked file, agents would fight over that lock constantly. Per-session files remove the fight.

The part that matters for your optimization

The activity log is already a push feed — the hook writes "made a plan / opened a PR" the moment it happens, and agents feed shows it without re-parsing any transcript. But walkthrough A (--active) ignores this and re-parses tails anyway. There's no database behind these logs and nothing pushes them to the live UI — that's the gap your "one stream → database → adapters" idea closes.

11

Ways the system reports "what's happening" — 3 in the CLI, 2 in the extension CLI EXT

The core issue, and it's inside the CLI itself: even in just the CLI there are three separate ways to answer "what's happening" that don't share a channel. The extension then adds two more.

#LayerChannelHow it works
1CLIpoll + re-parsesessions --active re-derives state on demand (the extension is what polls it)
2CLIthe event logsshared events.jsonl + per-session activity files → agents events
3CLIthe mailbox"this agent is waiting on you" → agents feed (feed.ts)
4EXTthe watchdognotices a stuck agent, pokes it over the socket (watchdog-server.ts:11)
5EXTthe file-watchernotices new session files, tells the editor windows

Focus on the CLI's three: 1 recomputes on demand, 2 is a written-down log, 3 is a mailbox — three answers to one question, no shared channel. Fixing that at the CLI (§13) is what makes the extension's job trivial.

12

The slow spots, ranked

Each one points at the code above. Ordered by how much it costs.

1The CLI recomputes live state on every call — and the poller does it every 3s CLI EXT

Root cause is CLI: sessions --active re-derives everything from scratch each call (re-parses tails, §6A) — there's no resident state. Multiplier is EXT: remoteSessions.vscode.ts:211 runs it every ~3s (:55), so a whole new process pays start-up + scan + parse, then exits.

Even without the extension — just you running agents sessions --active in a terminal — you pay the recompute every time. Several windows and machines only multiply it.

Fix (at the CLI): a resident CLI process holds current state in memory and emits what changed; every consumer (a terminal, the extension, another machine) reads that instead of triggering a fresh recompute.

2Asking the fleet starts one process per machine, per poll

Where: sessions.ts:28–36; each peer runs its own full agents sessions --local. The reused SSH connection (ssh-exec.ts:76) saves the handshake but not the remote start-up + scan.

Fix: each machine runs a small resident process that pushes only changes; the caller subscribes once instead of starting a process per poll.

3The same parsing logic is written in five places

Where: full parser parse.ts:143; the index scanner discover.ts:2227/2458; the Factory "which window" parser sessionParse.ts:46; the Factory activity-line parser session.activity.ts:93; the live tail renderer stream-render.ts:116. Each knows the harness formats separately.

Fix: one adapter per harness — { where the files are, parse the head, parse it all, read the id } — used by all five. Adding a harness (or fixing the Codex file-vs-id split) becomes one file, not five.

4The index only updates when someone asks, behind one lock, up to 5s late

Where: the scan runs on every agents sessions call, and only one process may scan at a time; a still-writing session's index can be up to 5s behind (discover.ts:65).

Fix: let the watcher (§8) update the index the moment a file changes, so reads are just database reads.

5The event logs have no database and nothing pushes them

Where: event-stream.ts:57 reads and sorts the file in memory; the shared log takes a lock on every write (events.ts:464).

Fix: put the events in SQLite (same trick as sessions) with a "what changed" feed. Now you get time-range queries, a subscribe channel, and no shared write lock.

6Two pid files, whole-file reads, and small copy-pastes

Where: the pid→id pointer is written twice (§1); parse.ts:130 reads whole files; resolveMode and the exit-file trick are each written twice (§10).

Fix: one pid file with two writers; read transcripts in pages instead of whole; move the duplicated helpers into one place.
13

The fix: compute once, hand it out — in the CLI CLI

Slow spots 1, 2, 4 and 5 are one problem: the live data is fetched and recomputed on every request, instead of computed once and handed to whoever asks. The fix belongs in the CLI — once the CLI can produce and push state, the extension "just groups and displays," which is the easy part.

  • One process parses each file once. The machine-wide watcher (§8) already watches every folder — let it be the one that reads and understands the files, and let the CLI use it too (today they're separate).
  • Write the result to one store others can subscribe to. Use the same SQLite trick sessions already use, with a "what changed" feed. The event names (events.ts:68) are already the vocabulary.
  • Readers subscribe; they don't start a process. The CLI, the extension, and other machines all read the same feed. The 3-second poll and the per-machine process both go away.
  • Each harness's format lives in one adapter. The store stays format-agnostic; one adapter per harness feeds it — your "different adapters per harness" — which also removes the five-places duplication and the Codex/OpenCode id quirks.
What it buys

Cost drops from "many short-lived processes re-parsing, per window, per machine, every 3s" to "parse once, then everyone reads what changed." Channels 1 and 2 (§11) become one. Teams and SSH (§10) don't change — they're already fine.
