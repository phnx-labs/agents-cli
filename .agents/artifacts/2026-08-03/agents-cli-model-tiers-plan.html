Pick a model by cost tier, not by a name that keeps changing

A stable cheap / default / best / ultra vocabulary across every important harness — Claude, Codex, Kimi, Grok, Cursor — resolved per version and ranked by price where it exists, catalog order where it doesn't.

  • Four tiers — cheap / default / best / ultra — across every harness
  • Ranking signal is per-harness — price where it exists, catalog order where it doesn't
  • Subscription harnesses (Grok, Kimi, Cursor) often expose 1-2 models — tiers collapse, honestly
  • Tiers resolve per (harness, installed version) and clamp when a tier is absent
  • agents models becomes the single source — every harness shows its own tier map

Purpose

When an agent runs a team (agents teams add <team> <teammate> <task>), it must decide which model each teammate runs on — for any harness it spawns, not just Claude. Today the only cost lever is --model <id> (teams.ts:1501), which wants a literal like claude-opus-4-8 or grok-4.5. That is the wrong ergonomic for an autonomous caller:

  • Names churn and differ per harness — opus-4-8, gpt-5.5, grok-4.5, kimi-code/k3. A stale id silently forwards (resolveModel(), models.ts:1030, never blocks).
  • Support varies per version. Each installed build ships a different model set, so the answer depends on the exact version the teammate spawns on.
  • Cost is the real axis, but there is no tier concept — and the billing differs per harness: Claude/Codex/Gemini are per-token API; Grok/Kimi/Cursor are subscription/quota.

Goal: one stable, cost-first vocabulary — --model cheap | default | best | ultra — that works across Claude, Codex, Kimi, Grok, Cursor (and the rest), resolving per (harness, installed version) to a concrete model that harness+version actually ships. Names never drift; an absent tier clamps; concrete ids keep working unchanged.

Verified live on this box. Grok exposes exactly one model (grok-4.5); Kimi one or two (kimi-code/k3) — both subscription harnesses, so $/token isn't even the right axis for them. Claude has a clean 4-rung price ladder, but agents models claude@2.1.219 extracts 0 models (the structured regex fails on the newest native binary) while a raw id scan of that same binary finds claude-fable-5, opus-5, sonnet-5. So tiering must (a) not assume price exists, (b) not assume four rungs exist, (c) not depend on the fragile structured catalog.

Proposed Changes

One pipeline, per harness: extract ids → rank → map to tiers → resolve. Make agents models the single source of truth — harden its extraction, rank each harness's catalog, and expose the tier map — then have model resolution consume the same computation.

Ranking signal is per-harness (not "always price")

A harness's models are ranked cheapest → most capable by the best signal available, in this order:

  1. Per-token price from prices.json (getModelPricing, prefix/suffix tolerant) — applies to Claude, Codex/OpenAI, Gemini. This is the principled signal and is needed for budgeting anyway.
  2. Catalog order + size tokens when unpriced — the harness's own model list order, plus a name heuristic (nano|mini|lite|flash cheaper; pro|max|opus|ultra|large dearer). Applies to subscription harnesses (Grok, Kimi, Cursor) whose models carry no $/token.
  3. The ranked rungs are collapsed by family (one representative per rung, newest id) and mapped onto cheap · default · best · ultra. Fewer than four rungs → tiers collapse: a single-model harness resolves every tier to that one model. agents models prints the exact per-harness mapping, so an agent always sees what each tier means for that build.

Harness coverage (the five named + the rest)

Harness Billing Ranking signal Models today Tiers resolve to
Claude per-token API price haiku · sonnet · opus · fable 4 distinct rungs
Codex per-token API price gpt-5.4-nano/mini · gpt-5.4 · gpt-5.5 ranked, ~3-4 rungs
Kimi subscription catalog order kimi-code/k3 (+ route) 1-2 rungs → collapse
Grok subscription catalog order grok-4.5 1 rung → all tiers = grok-4.5
Cursor subscription catalog order composer / auto variants ranked, collapse as available
others (opencode, antigravity, gemini) mixed price or order via same generic path resolve or fail-safe

Same code path for all — MODEL_CAPABLE_AGENTS (commands/models.ts:25), no per-harness if/else arms. A harness with no extractable catalog (droid, copilot, …) hits the fail-safe (flag dropped + warning) and still takes concrete ids.

Claude is one example of the price path

The Claude entries in prices.json already sort into the order you want, so no curated capability table is needed for it:

Tier Claude family Blended $/Mtok
cheap haiku ~$6
default sonnet ~$18
best opus ~$30
ultra fable ~$60 (newer builds; else clamps to best)

Build steps

  1. Harden extraction (all catalog kinds). Fix the Claude native-binary regression: add a direct id scan to extractClaudeCatalog (models.ts:380); broaden the keep-filter (models.ts:428) to fable|mythos. The cli-kind extractors (Grok/Kimi/Cursor/OpenCode) already spawn the harness's own models command — keep, and treat an empty catalog as the fail-safe, not a crash.
  2. Attach pricing where it exists. Add pricing? to ModelInfo; populate in getModelCatalog via getModelPricing(). Unpriced ids (subscription harnesses) carry no price — surfaced as —, never faked.
  3. New lib/model-tiers.ts — MODEL_TIERS, isTierToken, rankModels(agent, version) (price → catalog-order fallback → family-collapse), resolveTiers (map rungs onto four, collapsing when < 4), resolveTier with downward clamp (ultra → best → default → cheap).
  4. Wire the choke point. In resolveModel (models.ts:1030) resolve tier tokens to a concrete id — covers run and teams (both funnel through buildExecCommand, exec.ts:973). Add drop? so an unresolvable tier omits the flag (harness default) rather than forwarding a bogus "cheap".
  5. Surface it. agents models prints a per-harness tiers: block (with $/Mtok where priced) and emits it in --json; --model help on teams add + run names the tiers.

Public Interface

# same four words, every harness — the agent never spells a model id
teams add T claude "fix bug"  --model cheap    # → newest haiku the version ships
teams add T codex  "port it"  --model best     # → top-priced gpt the version ships
teams add T grok   "triage"   --model cheap    # → grok-4.5 (only rung; tiers collapse)
run kimi   "summarize"        --model default  # → kimi-code/k3
run claude "audit repo"       --model ultra    # → fable; or clamp → opus + a note

# discovery: the exact tier map for the version a teammate will spawn on
agents models grok --json       # tiers{cheap,default,best,ultra} = grok-4.5, pricing: null
agents models claude@2.1.219    # tiers block + per-model $/Mtok
  • Tier tokens accepted anywhere --model is: agents run, agents teams add, profiles.
  • Concrete ids behave exactly as today — additive, non-breaking.

Validation

  • model-tiers.test.ts (real path, no mocking):
    • Price path — a priced multi-model catalog ranks into four tiers (cheap=cheapest).
    • Collapse — a single-model catalog (grok-style) resolves every tier to that one id.
    • Unpriced fallback — a subscription catalog ranks by order + size tokens, not price.
    • Clamp — a Claude build with no Fable → ultra resolves to opus with clampedFrom.
    • isTierToken; family-collapse picks the newest id.
  • Extraction — the id scan yields a non-empty Claude catalog on a native-binary version; gated on isVersionInstalled so CI without an install skips.
  • End-to-end — agents models grok shows all four tiers = grok-4.5; agents models claude@2.1.219 lists models + tiers; run --model cheap resolves per harness; teams add --model best launches on the ranked model; bun run test:remote green.

Risks

  • Subscription harnesses have no $/token (Grok, Kimi, Cursor) — tiering ranks by catalog order + size tokens instead; with one model, tiers honestly collapse. Documented, not hidden.
  • Unpriced new families (e.g. a fresh opus-5) rank by family order until a prices.json entry lands — the same entry budgeting already needs.
  • Extractor fragility — the structured Claude extractor returns 0 models on 2.1.219; the id-scan floor both unblocks tiers and repairs that regression. cli-kind harnesses depend on their own binary being runnable — an empty catalog degrades to the fail-safe, never a crash.
