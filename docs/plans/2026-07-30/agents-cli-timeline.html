Your question, answered

“Is it re-parsing all sessions?” No. active.ts does not import discoverSessions — I checked its import list. It reads a bounded tail per live session: readSessionTailWithRaw (tail.ts:69) does a pread of the last 128 KB and keeps the last 60 events. On this machine that is 21 sessions × 128 KB ≈ 2.7 MB. That part is well built. The “loading sessions” you see is the 428 ms of setup before it starts.

The dumbest 123 ms

--active pays 123 ms to import discover.ts — 3,038 lines of incremental-scanner code it never calls. It is pulled in transitively for buildClaudeLabelMap (active.ts:29), a 28-line function that reads four small JSON files. Splitting that one function out of the module is a ~123 ms win on every --active, for a one-line import change.

The 127 ms: asking where files live, 26 times

This is where the version-home sprawl stops being a disk-space story and becomes a latency story.

$ agents sessions --roots --json
  16  claude          ← 1 live home + 15 version-home copies
   4  codex
   2  gemini · 1 antigravity · 1 droid · 2 kimi
  --
  26  total recursive fs.watch roots on this machine
  14  of them are version-home copies

Each root is a real directory that getSessionRoots() must stat on every CLI invocation — hence 127 ms. And each is also a root that the Factory monitor mounts a recursive fs.watch on, which on macOS is an FSEvents stream over the whole subtree. The claude version homes are 1.3 GB, 679 MB, 638 MB, 354 MB. You are running FSEvents over multiple gigabytes of transcripts that no one will ever open again.

Same root cause, different symptom

I framed version homes as an 80 GB disk problem last pass and you were right to push back — disk is cheap. But the same sprawl is what makes getSessionRoots() cost 127 ms per invocation and what multiplies your FSEvents watchers from 12 to 26. Pruning version homes is a latency fix. That is the argument I should have made.

03

The monitors — how many, and what happens with 10 agents

You asked how many file monitors are connected. The good news: this layer is the best-engineered part of the system. Watchers scale with roots, not with agents.

The counting rules

DimensionWatchersWhy
+1 agent on the same machine+0Roots are shared. terminalReadiness.ts:73 refcounts a singleton per root — added precisely because “with 20+ terminals open, the duplication caused observable system load.”
+1 VS Code window+0Leader election: one leader watches, followers subscribe (monitor/follower.ts:3).
+1 agent version installed+1 or moreEach version home is a new root. This is the only thing that actually grows the watcher count.
+1 machine in the fleet+26 (on that box)Plus one fresh subprocess per 3 s poll from every watching window.
10 agents, 3 machines, today~78≈26 per box — of which ~42 fleet-wide are stale version homes.
Credit

The dedup, refcounting, and leader election here are genuinely well done — someone already found and fixed the N-terminals-N-watchers bug. The watcher layer is not your problem. The problem is that this good push layer stops at the machine boundary, so cross-machine state falls back to spawning a process every 3 s.

But watching 10 agents is the cheap half

Everything above is the cost of observing agents. The cost of running them is separate, and it is worse — because it is paid per spawn, serially, before any agent does any work.

$ agents run --help        # prints help text. Starts no agent. Does no I/O.
  0.57 – 0.97 s

$ agents --version         # early-exits before the module graph loads
  0.09 s  (clean box)

Printing a help string costs 6–10× what --version costs. Nothing in run --help touches the database, the roots, or the disk — so that gap is eager module loading at CLI startup, before argument dispatch. It is the same 271 ms of imports from §01, plus the teams/exec/hosts graph, paid on every invocation of every subcommand.

The execution-path multiplier

That overhead is per agents run. Spinning up a 10-teammate team means the orchestrator assembles and launches ten agents run argv lines (teams/agents.ts:2219 buildRunArgv → :1799 launchProcess), so you pay it ten times — and for remote teammates it is paid on the remote box, after the SSH round-trip, inside the detached launch. Roughly 6–10 s of pure harness overhead before the first token of real work, growing linearly with team size.

The fix is §05 item 5, and it pays off far more here than on the status path: lazy-load the command modules so a subcommand imports only what it uses — resolve the subcommand first, then dynamic import() its handler. That turns a 10-teammate spin-up from ~10 × 0.9 s of import tax into ~10 × 0.1 s.

Measurement caveat — read this

The run --help numbers above, and a 7.55 s reading for agents devices, were taken while this machine sat at load average 27 — my own five background audits saturated it. Treat those absolutes as inflated upper bounds. The ratio to --version under identical load is still the real signal, and devices being an order of magnitude slower than every other subcommand deserves a re-measure on a quiet box — it is the command you run to see your fleet, and it should be instant. The §01 waterfall was taken before the audits started and is independently corroborated by the limit-1 vs limit-500 bisect, so it stands.

04

Search is broken — and it is a one-line bug

Found while scoping the session audit. This one probably costs you more daily friction than the latency does.

// at the SQL layer, the index is perfect:
SELECT COUNT(*) FROM session_text WHERE session_text MATCH 'login'   → 1,247 hits
                                                          'logged'   →   950 hits
                                                          'auth'     → 1,845 hits
11,685 rows carry content · average 42.7 KB each

// at the CLI:
$ agents sessions "login" --all --teams --limit 3
0 sessions.

The break is in discover.ts:351 searchContentIndex:

export function searchContentIndex(sessions: SessionMeta[], query: string) {
  const hits = ftsSearch(query);            // top 200 by BM25, across all 12,180 rows
  const byId = new Map(sessions.map(s => [s.id, s]));  // ← the ALREADY-FILTERED, ALREADY-LIMITED page
  for (const hit of hits) {
    const session = byId.get(hit.sessionId);
    if (!session) continue;                     // ← silently dropped
  }
}

Search results are intersected with a page that was computed independently. ftsSearch ranks the top 200 across the whole corpus; if none of those 200 happen to be in the current window, you get zero — even though 1,247 sessions match. The direction is backwards: the query should drive the result set (push the filter into the SQL and page the FTS output), not be filtered by a page chosen before the search ran.

Consequence

You are carrying a 760 MB full-text index (505 MB stored content + 256 MB inverted index) that answers correctly in SQL and returns nothing through the CLI. Fixing the intersection is a small change and turns a dead 760 MB into the feature it was supposed to be.
