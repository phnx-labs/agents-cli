Observability walkthrough · LangSmith

Are your agents’ failing tool calls actually surfacing?

Short answer: every failed tool call is captured — its arguments, its error, its timing. But a failure can sit inside a run that still reports success. Here is exactly where it shows, and where it hides, on your own traces.

THE CATCH THAT MATTERS FOR YOU

I ran an agent that calls two tools, both engineered to fail. LangSmith recorded both failures in full. Yet at the project level that run shows a green success and the dashboard reads Error Rate 0%.

The reason is the thing you’re hitting: when your agent catches a tool error (most agent frameworks do — they hand the error back to the model so it can react), the run is not marked failed. The tool failure is real and it’s in the trace — but you only see it if you open the run, or if you put a rule on the tool spans. Top-level “error rate” will not tell you your tools are failing.

01 / WHERE THE TRACES LIVE

Every run is a trace; every trace is a tree

In the left rail, Tracing → your project (agents-infra-dd) lists one row per agent run. Open one and you get the execution tree: the top node is the whole run, and each child is a single step — a model call (ChatOpenAI) or a tool call (web_search, write_file…). That tree is the unit of observability: it is literally what the agent did, in order.

02 / WHAT ONE TOOL CALL RECORDS

Arguments in, result out — for every call

Click any tool node and the right pane shows its exact input arguments, its full output, and its timing. Nothing is summarized away — below, the web_search node shows the precise query the agent passed and the digest it got back.

03 / THE TEST

Two tools, both rigged to fail

To answer your question directly I built a throwaway agent with two broken tools and traced one run of it:

  • run_code — catches the error and returns it as text (exit=1 … ReferenceError: db is not defined). This is how most coding-agent tools behave.
  • flaky_db — raises (connection timeout after 5000ms). This is how a raw DB/HTTP client behaves.
04 / WHERE THE FAILURE ACTUALLY SHOWS

The raised error gets a red tab — once you open it

Open the flaky_db node and it’s unambiguous: a dedicated red Error tab with the full message and stack, plus a red badge on the span. The failure is captured perfectly. The catch is that you had to drill two levels in to see it.

05 / THE GOTCHA, AT THE LEVEL YOU’D ACTUALLY LOOK

The run reports success. Error rate: 0%.

Here is the same failing run in the project list — the view you’d scan day to day. Green check, empty Error column, and the Stats panel reads Error Rate 0%. Both tools failed inside it; none of that reaches this level, because the agent caught the errors and finished.

06 / FROM SEEING IT TO FIXING IT

The tuning loop the trace unlocks

Observability is step one; the point is closing the loop. Once a bad run is in front of you, LangSmith turns it into training and regression signal:

  1. Flag it. Add feedback (👎) on the run, or select it and Add to Dataset — both are one click from the views above.
  2. Collect a set. Failing runs accumulate into a dataset of exactly the cases your agent gets wrong.
  3. Score it. Attach an Evaluator (e.g. “did every tool call succeed?”, “is the answer grounded?”) so each case gets a number.
  4. Change one thing. Edit the prompt in the Playground, or swap the model / tool.
  5. Run an Experiment over the dataset and diff versions — did the score go up, did tool failures go down, at what cost/latency. That diff is the tuning signal.
07 / FOR YOUR ACTUAL CODING AGENTS

One caveat before this helps your fleet

Everything above works because this agent is built on LangChain, which auto-instruments to LangSmith with two env vars and zero code. Your coding agents will only show up here if they emit traces. If they’re LangChain-based, same two env vars. If they’re not (Claude Code, a custom loop), you instrument them via OpenTelemetry export — LangSmith, Langfuse and Braintrust all ingest OTel. That’s the natural next step: point one real agent at a project, then put the per-tool success evaluator on it, and “which tool calls are failing” becomes a chart instead of a hunch.
