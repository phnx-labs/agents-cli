Enforcing invariants in agents-cli: why agent-authored changes regress

A design document. Agent-authored changes regress in a narrow, identifiable set of subsystems. This analyzes why, separates four independent causes, and sets out how each class of rule gets enforced — mechanically, at plan review, or at code review — given that the author and the reviewer are both agents.

Story

1. Context and problem statement

agents-cli is developed almost entirely by AI coding agents. The repository governs their work through a layered instruction system: a normative specification for six subsystems, ten architectural rules in the component memory file, a fourteen-item review contract, and roughly 57,000 words of fleet-level process guidance injected into every agent's context before it reads any code.

Despite that volume, changes in a narrow set of subsystems regress repeatedly. The pattern is concentrated rather than diffuse: over the last 120 days, the share of commits that are fixes or reverts is 50% in the daemon and in secrets/keychain, 44% in accounts and authentication, 40% in routines, and 38% in usage — against 36% in sessions, the most heavily specified subsystem in the repository.

The natural hypothesis is that instructions are too thin in the affected areas. The evidence does not support that hypothesis, and this document argues against it. Secrets is one of the most thoroughly specified subsystems in the codebase — 56 requirement identifiers, including explicit requirements governing interactive authorization prompts — and it has the joint-highest regression rate. Adding specification text is therefore unlikely to change the outcome.

What the affected subsystems share is not a shortage of stated rules. It is that their rules are stated but not mechanically enforced, and in three cases the rules themselves are ambiguous or describe behavior that does not exist yet. This document identifies four independent causes, each verified against the code, proposes changes for each, and sets out in §7 how a rule in this repository can be enforced at all — given that both the author and the reviewer are agents that may not follow instructions.

2. Goals and non-goals

Goals. Reduce the regression rate in the credential, daemon, routine and usage subsystems by converting stated invariants into mechanically checked ones. Make requirement identifiers usable as unambiguous references in review. Make it possible for an implementer to distinguish specified-and-implemented behavior from specified-and-intended behavior.

Non-goals. This document does not propose new instruction text, new process, or expanded review checklists. It does not propose restructuring the credential subsystem, changing the keychain access model, or altering the Touch ID authorization policy — the existing policy is sound and is not the problem. It does not address subsystems outside the identified cluster.

3. Background: how a change is governed today

Three tiers of instruction apply to code in this repository, and they differ sharply in force.

Tier 1, the normative specification (apps/cli/docs/specifications.md) defines 261 requirement identifiers across six subsystems — sessions, secrets, agent execution, scheduling, routine execution, and the watchdog. Requirements use RFC-2119 keywords, cite the implementing file:line, and carry Given/When/Then scenarios intended to map onto tests. A change that deviates from a requirement is a defect in either the code or the document, and the document says so.

Tier 2, the architectural rules (apps/cli/AGENTS.md, "Core design choices") are prose. All ten share one structural form: a given decision has exactly one home in the code, and a second home is the defect. Capability gating lives only in supports(); legacy path handling only in migrate.ts; the choice between native resume and /continue only in resolveSessionRecovery. The file states the consequence directly: "Break these and downstream code drifts silently."

Tier 3 is everything else. The CLI registers 100 top-level command names across 81 loader modules. Six subsystems have a specification. The remainder have, at most, a design document — and design documents in this repository are explicitly non-normative. This was verified directly rather than taken on the specification's word: hosts.md, teams.md and cloud.md contain zero capitalized MUST, SHOULD, or MAY between them, while using lowercase "must" in prose that reads as though it binds.

Coverage is uneven by design, but the uncovered set includes surfaces that act on other machines, hold durable state, or sit next to credentials.

4. Analysis

Four causes are separable. They are ordered by how much of the observed regression rate each plausibly explains.

4.1 An architectural invariant is stated but not enforced

The credential subsystem defines a single entry point for reading a keychain item. Requirement SEC-13 names it explicitly and states that the check happens before any helper process is spawned:

This covers raw item reads too, not just bundles: getKeychainToken/getKeychainTokens consult assertRawKeychainReadAllowed (lib/secrets/index.ts:877-899) BEFORE any helper process is spawned.

A second requirement, SEC-27, places a negative-result memo behind the same function so that a polling caller cannot re-raise an interactive authorization sheet every few seconds. Both protections are therefore reachable only through getKeychainToken. The design is sound.

Four non-test modules invoke /usr/bin/security directly and never reach that function: lib/agents.ts:1688, lib/usage.ts:3043, lib/auto-dispatch-linear.ts:26, and lib/openclaw-keychain.ts:276. On the first two, the only guard is an environment variable, AGENTS_NO_KEYCHAIN_PROBE, documented at agents.ts:1686 as existing for hermetic tests. The third has no guard at all and is reached from linear-project-counts.ts:222, a counting path that can execute unattended.

The invariant is architecturally correct and textually stated. It is not checkable, so it degrades one call site at a time.

The duplication is self-documented. usage.ts:3026 describes its own probe as mirroring the one in agents.ts, and the two implementations have already diverged in their arguments — usage.ts passes -w to retrieve the value, agents.ts omits it because it only tests existence:

// apps/cli/src/lib/usage.ts:3026 (comment) and 3040-3046
//  * the probe command pair mirrors antigravityOsKeyringProbe in agents.ts, with
if (process.env.AGENTS_NO_KEYCHAIN_PROBE === '1') return null;
const probe =
  process.platform === 'darwin'
    ? { cmd: 'security', args: ['find-generic-password', '-w', '-s', 'gemini', '-a', 'antigravity'] }
    : process.platform === 'linux'
      ? { cmd: 'secret-tool', args: ['lookup', 'service', 'gemini', 'username', 'antigravity'] }
      : null;

The observable consequence is a remediation loop. Twenty-five changes since 2026-05-21 name the interactive authorization prompt in their subject line, and the frequency is increasing rather than converging: three in May, four in June, six in July, and twelve in the first nine days of August. They are distributed across four subsystems — secrets, usage, devices and sync — which is what one expects when a policy is enforced at call sites rather than at a boundary. Two of them state the generalization explicitly and still did not close it: one is titled "close the same headless-prompt gap in the remaining background callers" (2026-07-16), and another, three weeks later, "stop background Touch ID prompt storms from raw keychain reads."

Frequency is the signal, not any individual change. Each of these was authored believing it addressed the cause.

4.2 Requirement identifiers are not unique

The specification states that identifiers are section-namespaced so that each one is globally unique. Five are not. SES-40 is defined three times, at lines 296, 481 and 660, with three unrelated meanings — account attribution, index authority, and focus/resume routing. SES-38 and SES-39 are each defined twice, as are SING-11 and SING-12. The collision is not cosmetic: SING-12 cites SING-11 in its own body, and SING-11 now denotes both "a single scheduled fire launches a routine at most once" and "at most one daemon is alive per state directory."

The practical effect is that an instruction of the form "satisfy SES-40" cannot be resolved by an implementer, and a review comment citing it cannot be resolved by an author. Both collision clusters fall in the daemon and routine subsystems, which are among the highest-regression areas.

4.3 Aspirational requirements are formatted identically to implemented ones

The specification supports a status marker distinguishing behavior the code exhibits from behavior it is intended to exhibit. In the routine execution section, eight of the eleven requirements carry [Intended]. The marker appears inline in the identifier line, in the form (MUST, [Intended]), which places it in the same visual position as the RFC-2119 keyword and makes it easy to overlook — including programmatically, as a regex matching (MUST) will not match it.

An implementer reading that section therefore encounters eleven statements in identical grammatical form, of which three describe the system and eight describe a target. Absent careful reading, an agent will implement against, or assert conformance to, behavior that does not exist.

Identifier Status Requirement, abbreviated
RT-1 implemented projects (plural) is grouping metadata only
RT-2 [Intended] The execution anchor is distinct from the plural grouping
RT-3 [Intended] The working directory is resolved on the execution target
RT-4 [Intended] A command routine (shell body, no agent) must …
RT-5 [Intended] add/edit verify readiness before accepting a definition
RT-6 [Intended] Every attempt is recorded as a RunMeta under .history/runs/
RT-7 [Intended] RunMeta.status distinguishes, at minimum, …
RT-8 implemented repo is an external identity, not a local checkout
RT-9 [Intended] resume re-runs the readiness check
RT-10 [Intended] A raw YAML edit must …
RT-11 implemented The menu-bar helper consumes state for display only

Across the whole document, sixteen requirements carry [Intended] and two carry [Drift]. Nine of the sixteen are in routine execution.

4.4 Coverage gaps adjacent to the credential boundary

The specification's own coverage inventory places the signed keychain helper and the wallet in the unspecified row, and names them among the five surfaces where the absence is most consequential, on the grounds that they "sit directly against the credential boundary that §Secrets specifies, without inheriting any of its requirements." The same row contains sync/apply/status, which reconcile configuration across every machine.

This is a real gap, but it is the weakest of the four causes on the evidence available: the subsystems with no contract at all (usage at 38%, sync at 34%) regress less than the heavily specified secrets subsystem at 50%. Coverage alone does not predict regression, which is the central reason this document does not recommend writing more specification as the primary remedy.

5. Proposal

5.1 Primary: make the credential entry point structurally singular

Add a build-time check asserting that no module outside lib/secrets/ invokes the keychain binary, implemented as a unit test in the existing suite rather than a lint plugin, so that it runs everywhere the suite runs and requires no new tooling.

The check enumerates source files, excludes lib/secrets/, and fails on any occurrence of find-generic-password, add-generic-password, delete-generic-password, or a direct /usr/bin/security invocation. It would fail today on the four modules in §4.1, so landing it requires routing those call sites through getKeychainToken first — which is the actual work, and is bounded: two of the four are the same duplicated probe and collapse into one.

An explicit allowlist should exist for genuine exceptions, keyed by file and reason, so that an intentional exception is a reviewed diff to the allowlist rather than an invisible new call site.

Why this rather than the alternatives. Three other options were considered.

Option Assessment
Restate the rule in AGENTS.md Rejected. The rule is already stated twice — in SEC-13 and in the "cross-cutting changes go to the source" review rule — and both were violated. Restating an unenforced rule does not change its enforcement
Add a review-checklist item Rejected. The fourteen-item review contract already covers duplicate code and cross-cutting changes. Reviewer attention is the mechanism that has been failing
Encapsulate at the type level (a branded credential type) Deferred. It is stronger than a test, but it constrains only the typed paths; a execFileSync('security', …) call remains reachable. It is a reasonable follow-on, not a substitute
A unit test asserting one entry point Recommended. Fails deterministically in CI, is cheap to write, requires no new dependency, and its failure message can name the correct entry point directly

Risks. The check is textual and can be evaded by constructing the binary name dynamically. This is acceptable: the objective is to prevent inadvertent recreation of a second path, not to resist a deliberate one. A secondary risk is false positives in documentation strings and test fixtures, addressed by scoping to non-test sources and by the allowlist.

5.2 Supporting: renumber the five colliding identifiers

Assign new identifiers to the duplicate definitions and leave the first definition of each in place, so existing citations continue to resolve. Add a test asserting identifier uniqueness so that the property is maintained rather than periodically restored — the same structural argument as §5.1, applied to the document.

The choice of which definition keeps the original number affects existing references in review history and in code comments, and is a judgment call for the specification's owner rather than one to make mechanically.

5.3 Supporting: separate intended from implemented behavior

Move [Intended] out of the identifier line and into a required trailing status line, and add a section-level summary stating how many of the section's requirements are currently implemented. An implementer should be able to tell, without reading every requirement body, that eight of the eleven routine requirements describe a target.

5.4 Explicitly not proposed: additional instruction text

Approximately 57,000 words of process guidance already precede every agent's first read of the code. None of the four causes above is an absent instruction. Each is an instruction that is stated and unenforced, ambiguous, or indistinguishable from an aspiration. Adding text addresses none of them and increases the context cost of every agent invocation.

6. Measurement, and its limitations

The regression rates in §1 are computed by attributing each commit to a subsystem by file path and classifying it as remediation when its subject begins with fix or revert or mentions a regression. The classifier is deliberately simple and has known biases, stated here so the numbers are read correctly.

A commit touching two subsystems counts for both. Conventional-commit prefixes are author-chosen and inconsistently applied, so a fix committed as refactor is not counted. Manual inspection of the two largest buckets found the classification sound: all 65 daemon remediations carry a fix prefix, and secrets contains exactly one false positive — a test-quarantine commit matched on the word "regressions" — giving 135 rather than 136.

The prompt-remediation count in §4.1 is subject-line matching and is a lower bound: it cannot see remediations that did not name the prompt.

One further measurement was tested and discarded. An earlier draft of this analysis proposed that the affected subsystems are those whose behavior cannot be asserted in CI, using the density of skipped tests as the proxy. Inspection did not support it: of 137 conditional skips in the suite, 117 are Windows portability guards. Only 20 are conditional on a capability the machine must have — seven macOS-only, five requiring the signed keychain helper, four requiring a reachable SSH endpoint, four requiring a POSIX shell — and they sit in secrets and hosts, not the daemon. The hypothesis is not disproven for secrets and hosts, but the metric that appeared to support it did not measure what it was read as measuring.

7. What to implement

Nothing in this repository is machine-checked against the twenty-four rules it states. This section specifies the checks to write, where each one lives, what it reads, and whether it passes today. Three existing mechanisms are extended rather than replaced.

Check 1 is the primary proposal from §5.1. Check 2 is the same idea applied to the specification instead of the code, and is the cheapest first commit: it needs no source changes and fails immediately on a defect the repository already has.

7.3 The plan requirement

Add a required Contract impact block to any plan for a code change, with four questions:

  1. Which requirement identifiers does this change touch? (If none — is the surface unspecified? Say so.)
  2. Which existing function owns each decision this change makes? ("None, I am adding one" is a valid answer; not asking is the failure.)
  3. Which boundaries does it cross — another machine, the OS credential store, a background process, another harness?
  4. How will the effect be verified, and on which machine?

The value is timing, not content. "I will read the token in usage.ts" is legible in a plan and invisible in a diff, where it is six ordinary lines. Question 4 is worth asking at plan time specifically: after the code exists, "this can only be proven on macOS with the keychain helper installed" becomes a reason to skip the test rather than a reason to arrange the machine.

Enforcement is a PreToolUse hook on ExitPlanMode, in the same position and form as the existing hooks under ~/.agents/.system/hooks/pre-tool-use/ (git-guard.sh is the working example): it inspects the plan text, and exits non-zero naming the missing block. The reviewer then checks four short answers against the specification rather than re-deriving them from a diff.

7.4 The review checklist

Extend scripts/ci-scope.ts with a reviewRules(changedFiles: string[]): string[] export that maps changed paths to the rules that can apply, and emit the result where the reviewer will read it. Concretely: a diff touching apps/cli/src/lib/secrets/** emits "verify SEC-13 and SEC-27 remain on the call path"; one touching a registry emits the parity question; one touching a documented flag emits the docs and changelog questions. Rules that cannot apply are omitted, not restated.

This replaces handing the reviewer fourteen prose rules plus a diff and asking it to work out which apply — the same open-ended task the author just failed. It matters more than usual at the moment: the repository's automated reviewer has been disabled since 2026-08-02 (#1767), so the non-author review is a subagent, and a subagent given the prose contract fails the same way the author did.

7.5 Checks that must land as ratchets

Two of the six fail on the existing tree for reasons that are partly legitimate, so they land with a recorded baseline that new code cannot add to.

Check Baseline measured today Landing form
Keychain access confined to lib/secrets/ 4 violating modules Fix all four, then land as a hard failure — the set is small enough to clear in one change
Non-trivial commands set setHelpSections 58 of 134 command modules Ratchet: the covered count may not decrease
No acting timer in apps/factory 9 setInterval sites, including a leader-election heartbeat (monitor/leader.ts:73) and a panel refresh (vscode/issuesPanel.vscode.ts:134) Ratchet plus a reasoned allowlist; a rendering poll is legitimate, a callback that spawns is not

A check that fails on arrival with no path to green gets disabled rather than fixed, which is worse than not having it.

7.6 The scheduled re-check

Add a workflow modeled on secret-scan.yml — cron plus workflow_dispatch — running checks 1 through 5 against the default branch and opening an issue when a new violation appears. This is the only check that observes the repository as a whole rather than one change, and it catches what merges when CI is skipped or a check is temporarily disabled.

7.7 Order of work

  1. Check 2 (specification hygiene). No source changes, fails today, demonstrates the mechanism.
  2. Route the four keychain call sites through getKeychainToken; land check 1 as a hard failure.
  3. Add the Contract impact block and its ExitPlanMode hook.
  4. Checks 3, 5, 6, then 4 with its allowlist.
  5. reviewRules() in ci-scope.ts, wired into the reviewer prompt or the subagent brief.
  6. The scheduled workflow.

7.8 What this does not solve

An agent that ignores instructions is not made compliant by any of this — it is made detectable. Checks 1 through 6 convert nine of the fourteen review rules from instruction-following into build failures. The remaining five stay judgment calls: no fallback band-aids, fail loud at boundaries, tests exercise the real path, and the two plan-time questions, all decided by a model that can be wrong. The expected result is that the mechanized nine stop recurring and the rest continue at roughly their current rate.
