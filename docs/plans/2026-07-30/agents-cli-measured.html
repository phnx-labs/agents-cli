Third pass · numbers, not reasoning

The bottleneck isn't the poll. It's 80 GB of data nothing ever deletes.

Both previous passes reasoned about performance from source. This one measures it — and the measurements reorder the whole list. The database is 1 ms. Cold start is 0.09 s. Neither is the problem. Meanwhile 505 MB of the index is a copy of text that is written and never read, 68% of the index rows are dead, and ~/.agents has grown to 80 GB with no retention policy anywhere.

01

The measurements

Every number below was produced on this machine, just now. The bisect is the important part: each row isolates one more layer.

WhatMeasuredReading
agents --version0.09 s Binary cold start. The installed CLI is a Bun-compiled single-file binary (__BUN segment), not Node — so “Node cold-start” is not a cost that exists here.
sessions --roots --json0.14 s Start + roots resolution, no DB touched.

sessions --local --limit 1 --json0.56 s The key result. Identical cost for 1 row and 500 rows → the ~0.42 s is a fixed per-invocation cost, not per-row work, and not the database.

Attribution, corrected

The report attributes the poll cost to “Node cold-start + discoverSessions scan.” Measured, the binary starts in 0.09 s and SQLite answers in 1 ms. Roughly 0.45 s of fixed setup and ~0.6 s of active-specific work account for essentially all of it. Building a daemon to avoid a 0.09 s cold start would be optimizing the one part that is already fast.

For scale: at a 3 s poll, 1.1 s of work is a ~35% duty cycle of one core, per host, per window, plus 151 MB resident each cycle. That is the real steady-state cost — and it is worth fixing. But the fix follows from what the 0.45 s is, which nobody has profiled yet (§07).

02

Where 813 MB actually went

The report says the index holds “metadata only.” Per-table dbstat says otherwise.

SELECT name, SUM(pgsize) FROM dbstat GROUP BY name ORDER BY 2 DESC

  504.9 MB   session_text_content    ← FTS5's stored copy of the text
  255.8 MB   session_text_data       ← the inverted index (this is the feature)
    7.6 MB   sessions                ← the actual metadata
      2.0 MB   idx_sessions_file_path
      0.8 MB   scan_ledger  ·  0.8 MB session_text_idx  ·  <1 MB each: 8 more indexes

99% of the database is the search feature, and 62% of it is a second copy of text that already exists on disk in the transcripts.

That copy is write-only

FTS5 stores the source text by default so you can SELECT it back for snippet()/highlight(). This codebase never does:

// the ONLY write — db.ts:598
INSERT INTO session_text (session_id, label, topic, project, content) VALUES (?,?,?,?,?)

// the ONLY read — db.ts:1313-1319
SELECT session_id, bm25(session_text, 5.0, 2.0, 1.5, 1.0) AS rank
FROM session_text WHERE session_text MATCH ? ORDER BY rank ASC LIMIT ?

// no snippet(), no highlight(), no SELECT content — anywhere
Highest value per line changed in the codebase

Declare the FTS table content='' (contentless) with contentless_delete=1. Ranking, MATCH, and BM25 weights behave identically — the only thing you lose is the ability to select the text back, which nothing does. −505 MB, ~62% smaller database, plus faster inserts and a far cheaper VACUUM. contentless_delete needs SQLite ≥ 3.43; this machine reports 3.53.2, and the existing DELETE FROM session_text WHERE session_id = ? (db.ts:596) keeps working with it. It's a schema-version bump (already at 13) and a rebuild.

03

The 80 GB — and the line of code that makes it immortal

This is the finding neither pass had, and it dwarfs everything else.

du -sh ~/.agents                          80 GB
  ~/.agents/.history/trash               46 GB   ← soft-deleted agent version homes
  ~/.agents/.history/versions            12 GB   ← live version homes (13 claude, 4 codex, 5 grok…)
  ~/.agents/.history/sessions            790 MB  ← the index
  ~/.agents/.history/backups             346 MB

individual claude version homes:
  2.1.187/home/.claude/projects          1.3 GB
  2.1.207/…                              679 MB      2.1.181/… 638 MB      2.1.220/… 354 MB

Every agent version upgrade snapshots a complete home directory, transcripts included. Thirteen live claude homes and twelve trashed ones, each carrying its own copy of that version's session history. Nothing reaps them — there is no retention policy in the codebase for either versions/ or trash/.

Why the index rows are immortal too

When a version is removed, db.ts:1349 updateSessionFilePaths repoints its sessions at the trash copy so reads keep working — and, in the same transaction, deletes their scan_ledger entry:

UPDATE sessions SET file_path = ? WHERE id = ?            // → …/.history/trash/…
DELETE FROM scan_ledger WHERE file_path = ?               // db.ts:1367

The intent is sound (“session reads still work from the trash path”). The consequence is not: trash is not a scan root, so those rows are never revisited, never refreshed, and never removed. Each version removal permanently deposits its sessions into the index.

The index, audited row by row

Cross-checked against the filesystem, independent of bucket:

  • 4,853 rows (40%) point at a file that no longer exists. Nothing ever garbage-collects them.
  • Only 3,753 of 12,090 paths (31%) have a scan_ledger entry — so the incremental mtime/size skip, which the report presents as the reason scans are cheap, covers under a third of the index.
  • Of the existing-but-unledgered files, a sampled check found 331 were realpath aliases (a false alarm I ruled out) and 3,421 genuinely unledgered — all in trashed version homes, exactly as the updateSessionFilePaths path predicts.
Net

Roughly 68% of the index is dead weight — gone or trashed. Every BM25 query ranks against it, every list carries it, and it is holding a proportional share of that 505 MB of write-only text.

04

Bottlenecks, re-ranked by measurement

The badge on the right is where the original report ranked each one.

1505 MB of write-only text in the index report: unlisted

dbstat: session_text_content 504.9 MB. Written at db.ts:598, read nowhere — the sole FTS query selects session_id and bm25() only (db.ts:1313).

Fix: content='' + contentless_delete=1. Identical search behavior, −62% database. One DDL change plus a schema-version bump. Do this first — it is the cheapest large win available.

2No retention policy anywhere — 46 GB of trash, 12 GB of version homes report: unlisted

Measured du: 80 GB total under ~/.agents. Individual claude version homes at 1.3 GB / 679 MB / 638 MB. No prune/reap/retention code path exists for versions/ or trash/.

Fix: a reaper with an explicit policy — keep N most-recent version homes and M days of trash; on eviction, delete the directory and its index rows. Ship it with an agents doctor line that reports the number so it can't silently regrow. Note the real design question underneath: a version home does not need to carry transcripts at all — separating “the agent install” from “the conversations it produced” removes the duplication at the source.

368% of index rows are dead; the ledger covers 31% report: partially, as #4

4,853 of 12,090 paths do not exist on disk; 4,426 point into trash; 3,753 have a ledger entry; 90 rows have file_path = ''. updateSessionFilePaths (db.ts:1349) deletes the ledger entry by design, and nothing re-creates it.

Fix: a GC pass (drop rows whose file is gone, unless deliberately retained), and stop treating file_path as both the identity and the location. Once a session has a stable ref independent of which copy of the file you happened to scan, the trash-repoint hack and the empty-path rows both stop existing.

4~0.45 s of fixed per-invocation cost that is neither startup nor SQL report: #1, mis-attributed

Bisect: start 0.09 s · roots 0.14 s · --limit 1 0.56 s · --limit 500 0.58 s · raw DB open+query ~1 ms. Cost is flat in row count, so it is setup, not query.

Fix: profile it before designing around it. Flat-in-N and non-SQL points at module-graph init, roots resolution across 13+ version homes, or the scan-claim path. If it is the version-home walk, fixing #2 fixes this too. Removing 0.45 s from every invocation takes the 3 s poll from ~35% to ~20% duty cycle without any new architecture.

5The 3 s poll itself — 1.1 s and 151 MB, × windows × hosts report: #1

Measured 1.04–1.17 s wall, 151 MB peak RSS, for 21 live rows.

Fix: still real, still worth fixing — but it is fourth, and the honest sequence is: fix #4 first, re-measure, then decide between a streaming fan-out and a full daemon. If #4 takes --active to ~0.3 s, a long-lived stream is plenty and the daemon never needs to be built.

6Four parsers / four location tables / two SQLite drivers report: #3

Carried over from the previous pass; unchanged and still verified.

Fix: as before — one manifest with a locate(), four storage-shape readers, one SQLite package. This is a correctness and maintenance win, not a performance one; rank it accordingly.
05

Where the report is mis-aimed

  • “Node cold-start.” The shipped binary is Bun-compiled and starts in 0.09 s. This cost does not exist, and it is the stated justification for the daemon.
  • “The index holds metadata only.” The metadata table is 7.6 MB of an 813 MB file. The other 99% is search, and most of that is redundant.
  • “scan_ledger means only changed files are re-read.” True for the 31% of rows that have a ledger entry. The mechanism is right; its coverage is not.
  • Bottleneck #5, “back the event stream with SQLite.” Measured, events.jsonl is 1.9 MB / 5,431 lines. A linear scan of that is sub-millisecond. Migrating it to a database is not a performance fix — argue for it on the subscribe surface if you want it, not on speed.
  • Bottleneck #6, “full-transcript render reads the whole file.” Correct, and it matters more than the ranking suggests now that we know claude transcripts total 354 MB in the live home alone — but the live path (readSessionTailWithRaw, tail.ts) is already bounded to a 128 KB pread tail. That part is well built; leave it alone.
Credit where due

The bounded tail read, the WAL + ledger design, the launchDetached single-implementation rule, and the argv-level coupling between run and teams are all genuinely good. The problems found here are accumulation and bookkeeping problems, not design failures in the hot path.

06

The architecture call

You asked for “highly performant, best architecture.” On the evidence, the best architecture here is mostly less, not more.

  • Do first — two config changes and a reaper. Contentless FTS (−505 MB), a GC pass for dead rows (−68% of the index), a retention policy for trash/ and versions/ (−46 GB). No architecture changes, no new components, no new failure modes. This is the entire size problem.
  • Then profile the 0.45 s. It is the only unexplained cost left, it is on every single invocation, and it is very likely tied to walking 13+ version homes — i.e. the same root cause as the retention problem. Measure, then decide.
  • Then, and only then, consider the transport. If --active lands near 0.3 s, a long-lived --watch stream over the existing ControlMaster channel is sufficient and adds no daemon lifecycle. Build the emit → DB → subscribe bus only if the numbers still justify it after the above.
  • Fix identity as the enabler, not as cleanup. A SessionRef that is stable across copies is what makes the GC safe, makes the trash-repoint hack unnecessary, and makes the harness manifest expressible. It is small, and three other fixes depend on it.
  • Question the version-home snapshot. The deepest fix: an agent version home should not contain the conversations. If transcripts lived in one canonical store and version homes carried only config, there would be no 46 GB, no duplicate indexing, no trash-repointing, and no ledger gap. That is the one change worth calling architectural.
07

What I could not determine

  • The composition of the 0.45 s fixed cost. I bisected to it but could not profile inside it — the installed binary is a Bun single-file executable, so node --cpu-prof does not apply and DTrace is blocked by SIP on this machine. To get it: build from source and run bun --inspect apps/cli/src/index.ts sessions --local --limit 1, or add a --timing flag that stamps the phase boundaries. That is the single highest-value next measurement.
  • Whether these ratios hold on other fleet hosts. Everything here is zion, which has 13 claude version homes and 12,180 indexed sessions. A worker box with two versions and 400 sessions will show a very different balance — worth running the same bisect on yosemite-s0 before committing to the ordering.
  • Post-fix sizes are projections. The ~95 MB figure in Fig 1 is arithmetic from the measured composition, not a rebuilt database. Verify by building the contentless schema against a copy.
