agents-cli architecture — accounts, usage, auth, run & teams

How the agents CLI is layered: one execution engine, four surfaces that drive it, the identity/capacity cluster (accounts, usage, auth-health, rotation) that decides which account each run lands on, and the teams pipeline that fans out over the same engine.

Story

The CLI has one spine and four mouths. Every agent invocation — whether you typed agents run, spawned a teams roster, fired a scheduled routine, or dispatched to another box over SSH — converges on lib/exec.ts, which builds the environment (swapping HOME to a per-version home), builds the argv, and spawns the harness binary.

Wrapped around that spine is the part you asked about: who does the run authenticate as, and does that account have headroom left? That is not one module but a cluster of five that feed each other — account-labels (identity), usage (capacity), usage-refresh (keeping capacity fresh cheaply), auth-health (is the credential alive), and rotate (the decision). The output of that cluster is a single choice — an agent@version whose version home holds the credential — which exec.ts then turns into a process.

Underneath everything sit four foundation modules that almost every file imports: state.ts (where config lives, layered project → user → system), agents.ts (the harness registry and capability table), versions.ts (version homes, installs, resource sync), and types.ts.

The agents run path, end to end

agents teams — a fan-out over agents run, not a second engine

The thing worth knowing first: a teammate is not a special kind of process. lib/teams/agents.ts:2740 builds ['run', target, fullPrompt] and routes it through getAgentsInvocation, so every teammate re-enters lib/exec.ts by the front door. Teams adds placement, isolation, and supervision around the same engine agents run uses — which is why a fix in buildExecEnv reaches teammates for free.

Placement is load-aware, and refuses rather than overfills
probePoolSignals (placement-probe.ts:107) probes the pool with an 8s timeout and a 15s signal TTL; pickLeastLoaded (scheduler.ts:200) ranks by max(loadPercent, memPercent) and breaks ties in declared pool order. When every device is at its agents.max-concurrent cap it throws with the per-device counts and the exact fix command — a hard error, not a silent overfill.
Worktree isolation fetches first and fails loud
createWorktree (worktree.ts:132) runs git fetch origin before branching and turns a network failure into a thrown error, with the reason stated in-code: "silent fallback to HEAD is how swarms write on a days-stale base and only discover it at merge time." Each teammate lands on agents/<name> at .agents/worktrees/<name>, based on origin/<default>.
The supervisor is what drains a DAG
runSupervisor (supervisor.ts:72) loops in waves, emitting a WaveSummary of pending/running/completed/failed/drained. A teammate declared with --after only launches when the supervisor advances the graph — which is why teams start --watch is required rather than optional, and why a forgotten one looks like a stuck team.
Budget is enforced twice, and it is cross-vendor
Once before launch — handleSpawn's pre-flight gate projects the teammate's estimated cost onto current spend and refuses on an on_exceed: block breach (#346) — and again during the run, via the supervisor's budgetWatcher, which stops the whole team on first breach (#399). A Claude teammate and a Codex teammate draw down the same pool.

How the pieces actually talk

Accounts are fingerprints, not credentials
account-labels.ts:16 hashes sha256(agent \0 accountKey) into a fingerprint, and ~/.agents/accounts.yaml maps a human label onto it. discoverAccounts() then finds every installed version signed into that same identity. OAuth credentials are never copied between homes — the label is a pointer, so agents run claude --account work resolves to a version home that already holds that login.
Usage is a registry with a two-tier cache
USAGE_SOURCES (usage.ts:337) maps 8 harnesses to a fetcher plus a network flag — codex and grok are parsed out of local session files, the rest are HTTP. Results are stale-while-revalidate: fresh under 5 min, served stale up to 24 h, and only then does a read block on a live fetch.
Auth health is a probe, not a badge
auth-health.ts:68 live-probes only claude, kimi and droid; verdicts are cached per host+agent+version (authCacheKey:301) so a fleet-wide view doesn't re-authenticate 40 installs. exec.ts closes the loop from the other side — AUTH_FAILURE_PATTERNS:2190 catches a dead credential in the running output and marks it.
The daemon is the only thing with a timer
One daemon per device claims a pid (claimDaemonInstance:373) and reaps strays. Its 8 ticks are the sole scheduler; UI surfaces (Factory, menubar, iOS Cockpit) only render CLI state and call CLI verbs. The usage-refresh tick is what keeps rotation's headroom numbers warm without a Touch ID prompt (fileOnly).
The one architectural invariant worth remembering: detection and decision live in the CLI; every other surface is a renderer. That is why exec.ts has four callers and no peers — a second execution path, or a second scheduler in a UI, is the double-fire bug class the repo's specification explicitly forbids.
