01

What agents-cli is

One command-line program to install, configure, run, and orchestrate many AI coding agents (Claude, Codex, Gemini, Cursor, OpenCode, Grok, Droid, …) — on one machine or across a fleet — plus a separate VS Code extension (Factory) that drives the same engine through a GUI.

05

Two programs, and the CLI's components CLI EXT

agents-cli is two separate programs: the agents CLI (apps/cli) and the Factory VS Code extension (apps/factory). They share no memory and no code — the extension runs the CLI as a subprocess and parses its JSON. The hook is a shell script the CLI installs into each agent's config. This doc is about the CLI.

06

Distributed execution CLI

The design's real spine: run agents on any machine in the fleet, without holding a live connection. Three shared primitives — buildRunArgv (the command), ssh-exec (transport), launchDetached (fire-and-forget) — carry every remote run and every remote teammate.

Topology — how work spreads across the fleet

Sequence — a remote teammate, start to done

  • Shared command — teams & --host both build an agents run … argv (teams/agents.ts:2219); teams never call the internal spawn.
  • Shared transport — one SSH primitive with connection reuse (ssh-exec.ts:76), one detached-launch helper for both run --host and teams (hosts/dispatch.ts:189, "lives in exactly one place").
  • Placement — pin → pool-of-one → fewest-running-teammates → local (scheduler.ts:76). Counts teammates, not real CPU/mem — a known gap.
07

Session identity — three writers CLI HOOK

"Which running process is which session?" A pid → session-id pointer, written to a file (never the DB — a pid is reused, so a saved row goes stale; reader.ts:113). Three things can write it, at different moments.

Who assigns the id differs per harness: Claude — we do (generate a UUID, pass --session-id, exact at launch). Codex/Cursor/Grok — the agent does; we learn it from its hook (stdin JSON, or env for Grok). Gemini/Antigravity — best-effort. OpenCode/others — no hook; discovered from the file. In teams, a Claude teammate's agent_id is its session id (agents.ts:1610); others stay split until discovered. Headless uses the same path. The two files hold the same data and could be one (two writers, one file) — joined by terminal_id/launch_id.

Reading & indexing: three walkthroughs CLI

The three things you do most. The chip on the right answers "re-parse a file, or just read the database?"

  • List / search — a SQLite read; only files whose size/mtime changed get re-scanned (db.ts:103 scan_ledger). Not a re-parse.
  • sessions --active — scans ps for live agents, maps pid→session, then re-reads the tail of each to infer working/waiting + tokens/sec (active.ts:389). Per machine, not per session; SSH fan-out for the fleet.
  • sessions <id> — DB lookup for the file path, then a full parse of the whole transcript (sessions.ts:1634). The DB never stores the body.
The exact answer

Listing = indexed DB read. Live status = re-parse the tail, per machine, every call. Reading one session = full re-parse. Only the last two touch a raw file.

11

Slow spots & the fix CLI

The distributed and session engines are well-factored. The cost is in producing the live "what's running" view — the code behind sessions --active — and it's in the CLI itself.

#Slow spotFix
1the CLI recomputes live state on every call — and the extension polls it every 3s, per machine, spawning a fresh process each time (active.ts:389, remoteSessions.vscode.ts:211)a resident CLI process holds state and pushes changes; consumers subscribe
2fleet --active spawns a fresh process on each peer per tickeach peer pushes deltas; caller subscribes once
3the same harness-parsing logic is written in ~5 placesone adapter per harness, used everywhere
4the index only updates when asked, behind one lock, up to 5s latelet the watcher update the index on file change
5the event logs have no DB and nothing pushes themback them with SQLite + a change feed

Scope of this doc

  • Covered in depth: the distributed execution engine (§6), session identity/storage/reading (§7–9), and the live-status + event system with its bottlenecks (§10–11) — the parts that carry the "run agents anywhere, see what they're doing" promise.
  • Overviewed: version management, config sync, secrets, cloud dispatch, browser/computer automation (§2) — named and placed, not traced line-by-line.
  • Deliberately out of scope: the Factory extension's internal UI, and the agent harnesses themselves (external systems in Fig 1).
