Six moves — and three things the report got vague or wrong

The original report's headline (poll → push) is right but it's the expensive fix. Underneath it sits a cheaper, more damaging problem the report only gestures at: nobody agrees where a transcript lives. Four separate tables answer that question, they cover different agent sets, and for OpenCode all three answers are different paths. That is the bug factory, and it's a week of typing, not an architecture rewrite.

00

Your three questions, answered from source

“Why does the report say stack?”

Because at that point the report was hand-waving. §1(b) says transcripts are “parsed by a completely separate stack” and never names it. Concretely, that “stack” is:

  • Indexer — apps/cli/src/lib/session/discover.ts (3038 lines), one scan<Harness>Incremental per agent, dispatched by a switch at discover.ts:234.
  • Full parser — apps/cli/src/lib/session/parse.ts (1653 lines), on-demand, whole-file.
  • Factory head parser — apps/factory/src/monitor/sessionParse.ts (240 lines), first 100 lines only.
  • Factory preview parser — apps/factory/src/vscode/sessions.vscode.ts (800 lines), including its own SQLite reader.

Four parsers, two apps, no shared interface. “Stack” was doing a lot of work in that sentence.

“Are different packages or libraries being used?”

Yes — two different SQLite implementations in the same monorepo.

// CLI — deliberately no native addon, no prebuild
apps/cli/src/lib/sqlite.ts:22   bun:sqlite under Bun · node:sqlite under Node ≥22.5
                                "Avoids the native better-sqlite3 addon entirely"

// Factory — WebAssembly SQLite, a separate npm dependency
apps/factory/package.json:1278  "sql.js": "^1.13.0"
sessions.vscode.ts:18           initSqlJs()  → reads Cursor's store.db
sessions.vscode.ts:731          await fs.readFile(dbPath)  // entire DB into a Buffer
But it isn't arbitrary

The split is defensible: the VS Code extension host pins its own Node, may predate node:sqlite (needs ≥22.5), and can't ship a native addon across platforms. sql.js was the right call for that constraint. The problem is that it's an undeclared fork — nothing says “extension host uses the WASM driver,” so the two will drift on schema, BLOB handling, and error semantics. And readFile-the-whole-DB is fine for a Cursor chat, fatal the day it points at OpenCode's global opencode.db.

“Session transcripts have no standardized place”

Correct, and it's worse than “no standard” — it's four tables that disagree. See §01.

OpenCode is the proof

// three answers, same repo, same agent
discover.ts:1451       ~/.local/share/opencode/opencode.db        // CLI: a global SQLite DB

The report is wrong here

The comment at sessionParse.ts:~196 justifies the hardcoded OpenCode path with “the CLI does not scan opencode transcripts, so it never appears in --roots.” It does — scanOpenCodeIncremental() is dispatched at discover.ts:240 and reads opencode.db. OpenCode is absent from --roots not because it's unscanned but because SESSION_ROOT_SPECS only models directory roots and OpenCode is a file. The extension then worked around a wrong diagnosis with two more wrong paths.

This class already bit you once

The source records it: “the hardcoded list kept watching ~/.gemini/sessions after gemini moved its transcripts to ~/.gemini/tmp” (sessionParse.ts:~193). That's the whole failure mode — a vendor moves a directory, one table learns, three don't, and a surface goes quietly blind. The fix (watcherRootsFromCli()) was right in shape and incomplete in coverage.

02

The six moves

Each with what it buys and — more usefully — what it costs. Ordered by leverage-per-risk, not by ambition.

1One harness manifest — but it needs a locate(), not a path string small · high leverage

Collapse the four tables into one HARNESSES[] entry per agent, covering all 11 (+ cursor), and make agents sessions --roots --json the only publisher. The plumbing already exists — watcherRootsFromCli() proved the pattern; it just reads from a table that's missing half the agents.

Buys — the gemini-moved-directory bug becomes structurally impossible. Adding a harness becomes one entry instead of four edits in two apps. --roots stops lying by omission.
Costs / watch out — a naive {agent, subdir} manifest is exactly what exists today and it's why OpenCode fell out: it can't express “one global DB file,” “one .db per trajectory” (antigravity), “dir-per-session with messages.jsonl” (rush), or claude's project-hashed dirs. Model it as a small locate() capability returning {kind: 'dir'|'file'|'glob', path}[]. If you ship a path-string manifest plus five exceptions, you've rebuilt today's problem with more ceremony.

2Four storage shapes, not eleven harnesses medium · kills the 4× parser dup

The report proposes one HarnessAdapter per harness. Go one level more abstract first: there are only about four physical shapes in play.

  • Append-only NDJSON — claude, codex, droid, grok, copilot, rush/messages.jsonl
  • One JSON doc per session — gemini
  • SQLite, one DB per session — antigravity (conversations/<uuid>.db), cursor (store.db)
  • SQLite, one global DB — opencode

Write four readers. A harness then declares (shape, locate, fieldMap) — data, not code.

Buys — new harness = a data entry, reviewed in a minute. The tail-read, head-read and full-read strategies get written once per shape instead of once per harness per call site (today: ~4× × 11).
Costs / watch out — two real limits. (a) Field mapping is lossy; keep a raw passthrough on every normalized event or you'll silently drop the harness-specific detail some surface depends on. (b) SQLite sources can't be tailed like NDJSON — WAL page writes don't map onto “bytes appended since offset,” so incremental reads need data_version/rowid watermarks, not byte offsets. Your unification will have a seam there no matter what; name it deliberately rather than discovering it at implementation time.

3One SQLite surface, hoisted into packages/ small · removes a silent fork

Move apps/cli/src/lib/sqlite.ts into a shared package and add a third backend: bun:sqlite → node:sqlite → sql.js. Factory imports the package instead of sql.js directly.

Buys — one BLOB/param/error contract instead of two that will drift. Factory gets the fast native path automatically when the extension host's Node is ≥22.5, and keeps working when it isn't. Also fixes the load-whole-DB-into-a-Buffer read at sessions.vscode.ts:731 for free on the native path.
Costs / watch out — sql.js genuinely can't do everything the native drivers can (no incremental BLOB I/O, no real WAL, whole-file-in-memory). A “unified” shim that pretends otherwise is worse than two honest ones. Make the capability explicit — db.capabilities.streaming — and let callers degrade, rather than papering over it.

4The extension stops touching transcripts at all medium · the biggest dup deletion

Today factory has its own roots tables, its own head parser, its own activity parser, and its own SQLite reader — while also shelling out to the CLI every 3s. Pick one. Make the CLI the only thing that knows a transcript format; the extension becomes a pure consumer of normalized rows.

Buys — deletes ~2 of the 4 parsers and 2 of the 4 roots tables outright. The whole class of “factory sees a different set of sessions than the CLI does” disappears. It also makes move 5 trivial, because there's then exactly one producer to stream from.
Costs / watch out — this hard-couples the extension to a compatible agents-cli version, and agents use switches version homes underneath it. You need (a) a declared protocol version on --roots/--active output and (b) a degraded mode when the CLI is absent or too old — watcherRootsFromCli()'s try/fallback is the right pattern, generalize it rather than dropping it. Do not delete the fallback in the name of purity; a VS Code extension that hard-fails on a stale CLI is a worse product than one that shows less.

5Stream the fan-out before you build a daemon small · ~80% of the daemon's win

The report's headline is “resident daemon + push bus.” Right direction, but there's a much cheaper step that captures most of it: keep the SSH fan-out, make the remote side long-lived — agents sessions --active --watch --json streaming NDJSON deltas over a single ControlMaster channel (ssh-exec.ts:76) that stays open.

Buys — kills the per-poll Node cold start and rescan on every peer, which is the dominant cost the report identifies (bottlenecks 1 and 2) — without inventing daemon lifecycle, leader election, or inbound connectivity. One process per host per subscriber, not one per host per 3s.
Costs / watch out — long-lived SSH channels need reconnect/backoff and orphan reaping (a dropped VS Code window must not leave a watcher running on yosemite-s0). And it moves cost from CPU to open FDs and idle processes across the fleet. Still far less new state than a daemon. The real argument for doing this first is that it forces you to define the delta format — which is the daemon's actual hard part, learned cheaply.

6Session identity is not a file path small · unblocks moves 1–2

The index is keyed on file_path (db.ts:103 scan_ledger), which assumes one file per session. Row-backed harnesses already break it — OpenCode sessions get a synthetic opencode.db#<id> composite key (discover.ts:1587). And canonicalLedgerKey (db.ts:28) exists purely to realpath version-home symlinks so agents use doesn't bust the cache — a second identity patch on the same assumption.

Buys — a real SessionRef {harness, sessionId, source} makes SQLite harnesses first-class instead of hacks, and makes the “where do transcripts live” question answerable uniformly across dir-, file-, and row-backed sources. Both existing patches collapse into it.
Costs / watch out — this is a schema migration on a live DB (SCHEMA_VERSION is already at 13, so the machinery exists, but every machine on the fleet re-indexes on upgrade — a visible one-time stall). Do it before moves 1–2 or you'll build the manifest against an identity model that can't hold it.
03

Order of operations

If you only do part of this, do the top half — it's most of the value at a fraction of the risk.

  • First — move 6 (identity), then move 1 (manifest). Small, mechanical, and they delete a live class of bug rather than optimizing a hot path.
  • Then — move 3 (one SQLite package) and move 4 (extension stops parsing). These are the dup deletions; they get easier once the manifest exists.
  • Then — move 5 (streaming fan-out). Measure after this. It may well be enough.
  • Only then — the daemon + event bus the report proposes. It's the right end state, but it introduces lifecycle, leader election, crash recovery, and version-skew problems that the current zero-background-state design deliberately avoids. Build it as an optional accelerator with the poll path retained as the fallback, so a dead daemon degrades to “slower” rather than “blind.”
Note

Nothing here touches §7 of the report — the teams / SSH / detached-launch layering. That part is genuinely well-factored (launchDetached “lives in exactly one place”), and the argv-level coupling between run and teams is a feature, not debt. Leave it alone.
