- **`agents daemon status` now reports a daemon running code that has been deleted (RUSH-2493).** A daemon keeps running from memory after its entry file is removed — so it answers every probe, `systemctl --user is-active` reads `active`, and the status command reported healthy, while the process cannot restart and is executing whatever was loaded before the delete. Observed on a dev box: a daemon ran 4h14m from a worktree that had been deleted, silently holding a second routine scheduler (the double-fire class the one-scheduler-one-executor rule exists to prevent), and nothing anywhere named it. `status` now carries a `Stale code` section listing each such pid with its missing entry, marks the `Binary:` line `(MISSING from disk)` when it is this device's own daemon, and `daemon doctor` counts it as a problem with the right remediation per case — `agents daemon restart` for your own, `kill <pid>` for a stray from a removed install or worktree. `--json` gains `binaryMissing` and `staleBinaries`. This is deliberately separate from duplicate detection: duplicates are a scope heuristic that RUSH-2368 had to narrow after a leaked test fixture was reported as a stray, whereas "the file is gone" is a filesystem fact that holds regardless of which HOME a process serves. Only absolute entry paths are checked, so a `node -e '<code>' __daemon-run` process is never mistaken for deleted code. Source: `apps/cli/src/commands/daemon.ts`, `apps/cli/src/commands/daemon.test.ts`.
