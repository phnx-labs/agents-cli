01Where the message dies

Nothing here is a rebuild. The block ledger and the sink fan-out were both built, on separate tracks, and never joined. Five breaks sit between them.

#BreakEvidence
1 A guard denial is a PreToolUse deny — a tool error, not a Notification. No trigger fires. git-guard.sh:327-330
2 Stop clears the attention sentinel, so explaining the blocker marks the session as not-needing-you. 06-attention-sentinel.sh
3 Blocks never broadcast. broadcastPostedEvent runs only for feed post; the six publishBlock calls never reach it. commands/feed.ts:366
lib/feed.ts:266,314,328…
4 The one block notifier is hardcoded to openclaw plus a hardcoded personal Telegram chat id, and only reachable via feed --dispatch, which no routine schedules. lib/notify.ts:46,74-78
5 Both escalation hooks look in the wrong resource layer — they default to the user layer, the skill ships in the system layer. 12-escalate-on-notification.sh:38
The one that matters most Break 5 is a one-token path bug. SKILL="${ESCALATE_SKILL_DIR:-$HOME/.agents/skills/escalate}" points at the user layer; the skill ships at ~/.agents/.system/skills/escalate. The [ -x "$SKILL/escalate.sh" ] || exit 0 guard on the next line has therefore exited silently on every box since the day it shipped. The escalation ladder is correct code that has never once run.

02How often this bites

Measured across the fleet, last 3 days, by scanning the final assistant message of every session transcript for a needs-you signature.

One of them names the failure outright — session 277c1709:

"rush message send doesn't exist either. No Telegram or iMessage reached you this session; I fell back to a desktop notification on workstation."

And agents are already hand-rolling a block channel out of the status channel. A live feed post reads:

"NEEDS Owner: factory-metrics report is in PR #182 … Owner owns the merge — I cannot self-approve my own PR. It also needs a one-time decision from him…"
This reframes the work Agents already have the habit and already write good blocked-messages. The instruction layer is largely working. What is missing is a typed channel for it, and delivery that isn't dead.

03The channels — three peers, not a primary with fallbacks

runFeedBroadcast already spawns each sink independently and reports each outcome, so the channels are genuinely redundant by construction. rush being unauthenticated degrades to Telegram plus desktop rather than losing the message.

SinkReaches you whenDependencies
desktop MenubarHelper --notifyat the Macnone — ships in the package
iMessage rush message sendaway from the deskrush installed + logged in
Telegram openclaw message sendaway, headless-safeopenclaw on the box

Desktop is the most reliable of the three — no network, no login, no external CLI — and it is already proven working. The agents-cli · custom harnesses are first-class now · PR #1746 merged to main entry in Notification Center is this exact path, branded with the agents-cli icon. It ships enabled by default.

Gap to close notifyDesktop is internal-only (lib/menubar/notify-desktop.ts:112), called from overdue.ts, heal.ts, run-notify.ts. There is no agents notify command, so the branded notification cannot be an argv-template sink today. PR 1 adds a thin wrapper — one mechanism, no special-casing. Separately, notification bodies truncate after roughly two lines, so a block's text must front-load the ask.

04The design

Layer 1 — the primitive

agents feed block "<what you need from the user>"
    [--option <label>...]     # answerable choices -> BlockOption[]
    [--default <answer>]      # safe default -> approval class + safeDefault
    [--timeout <minutes>]     # -> timeoutMinutes, feeds the existing policy engine
    [--json]
  • Writes an OpenBlock via the existing publishBlock, adding kind: 'declared' to the union at lib/feed.ts:74.
  • Post-and-continue, not halt. recordParked / recordContinued / recordDefaulted and feed-policy.ts's default-on-no-answer already assume non-blocking. Halting would fight the model and idle a whole session on one denial.
  • Fails loud only on total failure — non-zero when no sink is configured or every sink failed. One sink failing is a warning: a dead rush login must not mask a delivered notification.

Layer 2 — delivery: one mechanism, not two

  • blockBroadcastContext(block) in feed-broadcast.ts, adding {blockId}, {class}, {cost} and {focus} — the literal agents focus <id> string, so a phone message carries the exact command that unblocks it.
  • Delete notifyUrgentBlock's openclaw hardcode and the chat id, reimplemented over planFeedBroadcast / runFeedBroadcast. No personal chat id in an Apache-2.0 repo.
  • publishBlock stays a pure write; broadcasting fires only where a block newly becomes a needs-you, so stamping a lifecycle field can never re-page you.

05Adoption — how agents learn this

The half that decides whether the feature works. It is mostly rewiring things that already exist.

MechanismWhy this one
new A rule, rules/subrules/feed-blocks.md, modeled on feed-status-posts.md That template produced the 33 posts across 3 harnesses I measured. Rules are always in context.
edit no-permission-stop-guard.sh files the block from what the agent already wrote, then allows the stop It already regexes the final message for stall phrases and blocks with exit 2. It just routes nowhere.
edit 00-agent-verify-work-complete.sh:698-722 — fix a false claim It tells every agent feed post "can be forwarded to their phone". That is untrue today.
edit Layer-bug fix in both escalation hooks; report_friction added to the three guards missing it Makes the ladder run at all, and makes every guard denial observable.
The breadcrumb already exists git-guard.sh:53-64 already fires agents _internal friction --surface guard --id <failureId> on every deny, landing a structured record in ~/.agents/events.jsonl via emitFriction (lib/events.ts:760-769). The denial that blocked session session-id almost certainly left a machine-readable trace. Nothing consumes it. The stall guard reads that log, which makes the capture precise rather than heuristic.
Why a CLI verb, not a hook Hook events are badly non-portable. Only Claude fires Notification; only Codex fires PermissionRequest; Copilot is the only third-party harness covering both. Grok, Antigravity, OpenCode, Kiro, Goose, Cursor and Hermes each cover a different partial subset, and unmapped events are dropped silently. A hook-triggered design can never reach parity. A CLI verb is harness-agnostic by construction.

07Verification

Nothing here is done until a block filed by a real agent reaches a real device.

  • Unit — bun run test:remote. Real-path tests per the no-mocking rule: a block written to a temp feed dir, planned against a real sink config, with a sink argv that writes a file.
  • Fail-loud — unset the sink config, run feed block, assert non-zero and the "recorded but NOT delivered" message. This is the regression test for the bug that started all this.
  • Real delivery — confirm the iMessage arrives. A clean exit is not proof; check rush http GET /api/v1/channels/imessage/status returns "linked": true and wait for you to confirm receipt.
  • Doctor — agents doctor reports rush/openclaw missing with a runnable remediation on the boxes that lack them.
  • The 74a4893f replay — trigger a real git-guard force-push denial in a throwaway worktree, let the agent stop, and confirm the stall guard files a block that reaches both the phone and Notification Center. This is the acceptance test.

Decisions I made — redirect me if any is wrong

  • PR 1 excludes the menubar. It is a Swift surface I cannot build or eyeball from this Linux box; it needs workstation or release-host. Say so if you'd rather have click-to-focus in one shot and I'll do the whole thing on a Mac.
  • The Stop gate captures, it does not block. The agents' explanations are already good; a third blocking Stop gate on top of the two that exist invites loops.
  • Blocks always broadcast at important. A block is by definition worth interrupting over, so there is no per-block level flag to get wrong.
