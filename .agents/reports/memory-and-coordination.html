agents-cli · memory & coordination · field notes

How a fleet of agents shares memory
and coordinates across machines

One person runs many coding agents across many machines they own. Nothing here is a cloud broker: there is no central server, no fleet enumeration, no shared relay. Yet the agents still need to remember what they did, find each other's work, and answer each other's questions — across boxes that sleep, move networks, and go dark. This is how agents-cli does it today, what is real versus planned, and where the seams still show.

01The problem: one owner, many machines, many minds

Start with the shape of the day. You are sitting at a laptop. On the desk next to it a Mac mini is always on. In a rack somewhere are eight Linux boxes. Each one can run a coding agent — Claude, Codex, Grok, Kimi — and often several at once. You dispatch a task to whichever box has the headroom, walk away, and come back an hour later.

Three questions now have no obvious answer. What did that agent do? The transcript is a file on a machine you are not sitting at. Which of my agents is stuck? One of them is parked on a question, waiting, and you don't know which. How does the agent on box A answer the agent on box B? They share no memory and no channel.

The cloud-agent platforms answer these by owning the machines: a central control plane holds the sessions, a broker routes the messages, a vendor sandbox runs the work. agents-cli inverts that assumption. You own the machines; SSH reachability is the trust model; secrets never leave the box. The engineering problem is to get durable memory and real coordination out of that constraint, not despite it. The rest of this document is the answer, in three parts: how a session becomes memory, how that memory travels, and how one agent reaches another.

the one idea There is no coordinator. Every machine is authoritative for its own sessions; shared views are assembled on demand (SSH fan-out) or converged without conflict (a grow-only set in object storage). Nothing in the system needs a machine to be up for another machine to make progress.

02Two meanings of the word "session"

Every confusion about memory in agents-cli dissolves once you separate the two things the word "session" names. They have different lifetimes, different stores, and different failure modes.

  • A live identity — which process, on which machine, is which session right now. It exists only while the agent is running. It is a cache keyed by PID, and it is recomputed, never trusted stale.
  • A durable transcript — the conversation itself, on disk, indexed for search. It outlives the process, the reboot, and (optionally) the machine. This is the memory.

03Live identity: liveness you ask for, never liveness you keep

The live layer is deliberately dumb, and that is its strength.

When an agent launches, the CLI drops a small entry into a per-PID cache under terminals/by-pid (pid-registry.ts:91) — best-effort, it never throws (pid-registry.ts:100). For Claude the exact session id is known at spawn (the CLI mints the UUID and passes --session-id); for every other harness the launcher never receives the id, so the entry holds pid + agent + cwd and the id is recovered later from the transcript on disk. The middle link in that recovery chain is the working directory: pid → cwd → transcript file → id.

Liveness itself is not a state machine. Every agents sessions --active call recomputes it: isPidAlive (active.ts:528) issues process.kill(pid, 0) (active.ts:531) and guards against PID reuse by comparing the process start time (startedAtMs). Nothing is persisted. The question the system answers is "is this PID alive right now," never "what happened to it." The honest cost of that simplicity: a crashed agent doesn't leave a tombstone — it just stops appearing in the list, and crash-versus-clean-exit is indistinguishable.

a real seam A SessionStart hook would let a self-id'ing harness report its exact id at the source — collapsing every harness up to Claude's precision. It is built but not wired in. Until it is, non-Claude ids are recovered heuristically from disk.

04The durable transcript: turning conversations into searchable memory

The memory is the transcript, and the index over it is a plain SQLite database — no embeddings, no vector store, no model in the hot path.

The index lives at ~/.agents/.history/sessions/sessions.db, currently SCHEMA_VERSION = 21 (db.ts:26). The sessions table carries the metadata you sort and filter on — topic, cost, PR, plus provenance columns like actor and initiated_by. Full-text search rides an FTS5 virtual table, session_text (db.ts:102), and results are BM25-ranked with deliberate column weights — [5.0, 2.0, 1.5, 1.0] for label, topic, project, and body (db.ts:48). A label match outweighs a body match five to one, because that is what a human searching their own history actually wants.

Search is a database read. Opening one session is a full parse of that transcript from disk — the DB never stores the conversation body. And the index only touches files whose size or mtime changed (scan_ledger), so listing 500 sessions is not 500 re-parses. Each harness stores its transcripts in its own layout — one JSONL file per session (Claude, Codex), a directory of artifacts per session (Kimi, Grok), or a SQLite database (OpenCode, Antigravity) — and a per-harness scanner normalizes them into the one index.

05Cross-device memory: a grow-only set in object storage

A transcript indexed on one box is memory for that box. To make it memory for the fleet, agents-cli uses the one data structure that never needs conflict resolution.

The insight is that a transcript is append-only. Events are added; nothing is ever mutated or deleted. That makes a session a grow-only set (G-Set) — a CRDT whose merge is simply set union (crdt.ts:1). Two machines that each hold a copy of the same session can merge them by unioning their events, sorted deterministically by (timestamp, hash) (crdt.ts:108), with a fast path when one copy is already a superset of the other (crdt.ts:97). There is no "who wins" question, because both are right.

Transport is opt-in R2 (S3-compatible object storage). Each machine pushes only to its own prefix — sessions/<machine>/<agent>/<sessionId> (agents.ts:236) — so no two machines ever write the same object (sync.ts:4). The bodies are sealed client-side with AES-256-GCM (transcript-crypto.ts:30), the key resolved locally from an R2_SYNC_ENC_KEY bundle; the store sees ciphertext. Convergence is eventual, not real-time: the store is a durable mailbox for history, not a live wire.

06Coordination: three primitives, different in kind

Memory is half the story. The other half is one agent reaching another. agents-cli has three ways, and the important design decision is that they are not a menu you pick from — they are matched to the recipient's state.

PrimitiveWhat it isStoreCross-machine?
feed "A bulletin board you pull." Open blocks (last-writer-wins state: "this agent needs you") plus status posts (append-only events). .history/feed/, .history/activity/ Blocks: yes (SSH fan-out). Status posts: no — local-only lane.
mailbox "Private mail dropped into a running agent," drained at its next tool call. .history/mailbox/<id>/{inbox,processing,consumed} Yes, via --host SSH re-exec — the spool is written on the box that owns the agent. No shared relay.
session-inject "Types the answer straight into a parked agent's live terminal" when there is no next tool call to drain a mailbox. the live terminal (tmux / iTerm / pty) tmux / iTerm: yes over SSH. pty: local-only.

Their stores mirror their natures. The feed is two files because it is two ideas: an OpenBlock is state ("still blocked" overwrites "blocked"), while a status post is an event (append-only). The mailbox is a three-stage spool — inbox → processing → consumed (mailbox.ts:78) — with a claim-first drain (mailbox.ts:245) so a message can never be delivered twice or to the wrong agent. Inject has real backends: tmux send-keys and iTerm osascript … write text are shipped; pty write is shipped; the VSCodium URI backend routes on the CLI side but the extension still no-ops the verb, so it is not yet live.

07The router: how a message finds a mind

You do not choose feed vs mailbox vs inject. agents message inspects the recipient and routes. The precedence is four rules, first match wins (answer-router.ts:123).

08The fleet view: assembled on demand, fired exactly once

With no coordinator, "what is my whole fleet doing?" is answered by asking every box at once and merging the replies.

Both the live view and the feed use the same move: an SSH fan-out that runs the same command on each reachable device and merges the host-tagged results (gatherRemoteAgentsJson, remote-agents-json.ts:74). An agent posts progress on whichever box ran it — agents feed post appends a status.posted milestone; --blocked writes a status.blocked event plus an answerable OpenBlock and broadcasts the literal agents focus <id> command to run — and the fleet's posts merge into one recency-ordered list on read. A dead or slow box simply contributes zero rows; it never blocks the view.

For reactive coordination there are monitors: watch a source, detect a change, fire an action (spawn an agent, run a routine, send a notification, POST a webhook). Because a monitor config syncs to every machine, firing it everywhere would fire it N times — so each monitor names a single owner device and only that machine's daemon evaluates and fires it (monitors/config.ts:192). That pin is the exactly-once guarantee for v1; there is no distributed lock, by design.

the honest gap in the fleet view Status posts are written to a local-only activity lane; the feed's SSH fan-out carries only open blocks. So "who needs me" travels the fleet, but "here's what I just finished" does not — yet. Closing that is the first job of the context plane below.

The proposed direction is coherent and modest: do not build a broker. Extend the activity event stream that already exists, emit a few missing event types, and publish a small non-sensitive metadata manifest per machine to a private GitHub repo — reachable even when SSH is partitioned — with the always-on Mac mini keeping a warm cache. Transcripts stay local or in R2; only lightweight metadata travels through GitHub; every device stays authoritative for its own sessions. It is the same grow-only, no-coordinator philosophy pushed one layer up.

10Performance: what indexing and querying actually cost

You asked the sharp operational question: how long does it take to index a session and to query, and how do we make querying faster? Here are measured numbers from this box, plus the documented internals — labeled so you can tell which is which.

0.76 s
local warm query, --local (full-text, 50 results)
8.6 s
default query — it fans out to the whole fleet over SSH
~48 s
first cold call (SSH connections not yet warmed)
661 MB
sessions.db on this box

The headline is a 10× gap that has nothing to do with the index: the default query fans out to every reachable box and merges the replies, so wall-clock is bounded by the slowest peer (and a 12 s per-host timeout), not by SQLite. Add --local and the same query is sub-second. The index itself is not the bottleneck — and it is not re-parsing anything. Listing only re-scans files whose size or mtime changed (the scan_ledger), so a 661 MB database is a read, not a re-parse.

Coordination-path latency, measured

The same local-vs-fan-out shape holds across every read surface an agent uses to coordinate. Median of three runs on this box; the fleet column is the default SSH fan-out across ~11 boxes.

SurfaceLocalFleet fan-outWhat it answers
Session query (FTS)0.76 s8.6 s"find the session about X"
Live status --active~3.0 s~10 s"who is running right now"
Feed read~3.2 s13–22 s"who needs me / what happened"
Mailbox read (spool)~2.9 sno fan-out — agents ssh"my pending messages"

Three things fall out of the measurement. Every surface is sub-4 s locally and multiplies 3–7× under fan-out — the tail is remote work, not the local read. The fan-out is partition-safe in practice: on these runs three boxes (bismas-macbook-pro, winbox, gpu-box) were unreachable and were skipped, not waited on — the live proof of the "dead boxes contribute zero rows, never block the view" claim from §08. And the surfaces differ in what fan-out even means: the mailbox spool has no built-in fan-out — the mailboxes command takes no --host, so a peer's box is reached with agents ssh, unlike feed/sessions/activity which carry -H/--host natively. The per-host SSH timeout is 12 s (remote-agents-json.ts:18), but that is a per-host cap, not the total: the feed read's wider spread (13–22 s) reflects that it does more per peer than a session query — reading each reachable box's block and activity state — so the total is the summed work across all reachable peers, not a single capped wait.

How to make querying faster

  • Scope to the box when you can. --local skips the SSH fan-out entirely — the measured 10× win. Reach for the fleet view only when you actually need it.
  • The index is already incremental. The scan_ledger re-scans only changed files, so indexing cost is proportional to new transcript bytes, not the 661 MB total. The "is it re-parsing everything?" worry is unfounded — the measured cost is ~271 ms loading code and ~127 ms resolving paths, per the timeline profile.
  • Amortize the fixed ~400 ms startup. Today the menu-bar and extension re-poll by spawning a fresh process every 3 s, per machine — paying that startup over and over. The proposed fix is "parse once, push changes, subscribe": a persistent reader that pushes deltas instead of being re-invoked. That is the single biggest available speedup for the live view.
  • Keep the fan-out bounded. The 12 s per-host timeout and "dead boxes contribute zero rows" behavior already stop one asleep laptop from hanging the whole fleet query.

Each session was indexed, searchable, and readable from either box — the transcript layer doing exactly its job at fleet scale. What that snapshot does not contain is a measurement of the coordination path itself: there is no benchmark of sync latency, mailbox delivery time, or fan-out cost. That is the most valuable missing number, and the clearest next experiment — instrument a push, a pull-merge, and a cross-box agents message, and put real milliseconds on this diagram.

where this leaves us The memory layer is real and proven at scale. The coordination layer is real and state-aware. The two known seams — status posts that stay home, and no partition-tolerant recall — are exactly what the proposed context plane targets, and neither requires a coordinator to fix.
