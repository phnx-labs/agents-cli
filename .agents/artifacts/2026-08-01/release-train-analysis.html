agents-cli · release pipeline · plan

Stop every agent from releasing.
Give the release to one train.

Since the fleet scaled up, the npm publish stopped happening: on 2026-08-02 four release attempts produced zero published versions, and main now sits three versions ahead of the registry. The cause is not a slow pipeline. It is N agents each believing the release is their job, with nothing preventing two of them from running it at once.

This is not a theory about what might happen with concurrent agents. It is in the transcripts, timestamped.

The guard is correct. It is doing exactly what it should: refusing to publish a tree that differs from the one CI tested. The defect is that nothing prevented the concurrency in the first place, and nothing owns the half-finished release afterwards.

04Three root causes

1. Every agent thinks releasing is its job — because we told them so

The release-to-fleet rule in AGENTS.md says a merge "implicitly authorizes the rest of the chain" and that stopping at merged is "a banned stop". That rule was written for one agent working alone, where it is correct. With 10+ agents merging into the same repo, it instructs all ten to drive the release train simultaneously. This is the primary cause, and it lives in the memory file, not the code.

2. release.sh has no mutual exclusion

Grepping apps/cli/scripts/release.sh (1,004 lines) for flock, lock, or mutex returns nothing but comments about concurrent-merge drift. The script handles the symptom (it detects a drifted tree and refuses) but never claims exclusivity. Two agents on two machines can and do enter it at once.

3. A failed release leaves an orphan, and the next agent bumps past it

When the publish gate refuses, the version stays merged and tagged but unpublished. The next agent runs validate-bump.sh, sees main at 1.20.80, and cuts 1.20.81 rather than finishing 1.20.80. Repeat three times and you get today's state: npm at .78, main at .81, an open PR for .82. The queue drains backwards.

what is not a root cause The crabbox (3 min), the pipeline design (the self-routing home base is sound and the tree-match guard is what kept a bad publish from shipping), and reviewer latency. Do not rewrite these.

05The fix — three layers

Policy stops the contention, a lease makes it enforceable, and a scheduled train makes releasing someone's actual job instead of everyone's side quest.

Layer A — policy: a feature agent's job ends at merge

Rewrite the release-to-fleet rule so the ship chain is the release train's contract, not every agent's. A feature agent is done when its PR is merged and it has added a changelog fragment. It does not run release.sh. The rule keeps its teeth for the one role that owns releasing.

Layer B — mechanism: an origin-side release lease

The lock must live on origin, not on a filesystem — agents run on workstation, release-host, worker-s0/s1, and Hetzner boxes, so flock cannot see across them. A git ref is an atomic compare-and-swap that every box already has credentials for:

# claim: fails if another releaser already holds it — this is the mutex
git push origin HEAD:refs/release-lock/claim # non-forced push to a fresh ref = CAS

# the lease carries who/when/what, so a stale one is diagnosable
holder=$(hostname)/$AGENT_SESSION_ID  version=1.20.82  claimed=2026-08-02T04:00Z

# released on success OR failure via a trap; a lease older than 45 min is
# reclaimable, and reclaiming logs the stale holder rather than silently stealing

Second requirement on the same layer: resume before you start. If npm's latest is behind main and an unpublished v* tag exists, release.sh must finish that version rather than cut a new one. This is the check that would have prevented .79 → .80 → .81 stacking up.

Layer C — cadence: a scheduled release train

Run the release as a routine on release-host. It is already the home base: it holds the Developer ID cert and the npm token, so there is no ssh hop and no Touch ID prompt. The routine holds the lease for its whole run, so an agent that tries to release mid-train is refused by Layer B rather than by luck.

CadenceEffectVerdict
Nightly (1×/day)npm up to 24h behind main. At the observed rate of ~6 merges/day that is a large batch and a wide blast radius per release.too slow
Every 4 hours6 trains/day, matching the observed merge rate. npm at most 4h behind. Each release stays small enough to bisect.recommended
On-merge, queuedLowest latency, but 40 min of pipeline per merge means the queue never drains at 6 merges/day, and each run burns a crabbox.later, if needed

The train skips itself when there is nothing to do: if main's version equals npm's latest and no unpublished tag exists, it exits without provisioning a crabbox.

Layer D — fix the Windows flake that is blocking today's release

layer D — the release is blocked by something bigger than a flake Dispatching ci.yml manually on main (run 30734112958) shows macOS and Windows both failing, Linux green. The failure is setup.test.ts › agents setup secrets › makes future secrets create/import use the saved backend default: on macOS the secrets create path reaches for the signed Keychain helper app, which no CI checkout has (it is built and codesigned only during release), so readBundle() returns nothing and the assertion fails. Linux never needs the helper, so it stayed green and the PR merged.

The question worth settling is which thing is actually broken: a file-backed bundle should arguably not touch the macOS Keychain helper at all, which would make this a real product defect on any Mac whose install lacks the signed bundle, not just CI.

Separately and still unexplained: a vitest worker-fork crash on Windows after a fully green suite (7,358 passed, 0 failed, then Worker exited unexpectedly → exit 1). Which test leaves the handle is not identified; [worker] is in the fleet but its SSH credential is not in agents secrets, so the available repro path is workflow_dispatch iterations. Retry-looping the job would be a band-aid over an unknown crash and is not proposed.
the structural gap that let it through ci.yml runs the cross-platform matrix only on release/** branches and v* tags, never on PRs to main — deliberately, because macOS is billed 10× and Windows 2×. The cost reasoning is sound; the consequence is that a PR can merge fully green and break the release, and it surfaces days later as a blocked publish attributed to nobody. A cheap middle ground is one macOS leg on PRs to main, or a nightly matrix whose red is attributed to the PR that caused it.
