01Two id models — who chooses the session id

Binding a live process to a session needs two things. The PID is always known (the parent learns it from spawn(), exec.ts:1004). The session id (a UUID) is where harnesses split:

  • Model A — launcher assigns it (Claude only). The CLI mints a UUID and passes --session-id <uuid>; it's hard-gated to Claude. So the exact id is known at spawn and stored in by-pid. exec.ts:814-816, :1269-1271
  • Model B — agent mints its own (all other harnesses). codex, kimi, grok, gemini, opencode, antigravity, cursor generate the id internally. The launcher never receives it → the by-pid entry has sessionId: ∅ (pid + agent + cwd only). The id is recovered afterward, from the transcript on disk. exec.ts:1367 · pid-registry.ts:26

02Transcript storage layouts — four categories

A transcript storage layout is the triple {directory structure, session-id encoding, serialization format} a harness uses to persist a conversation. Every harness uses exactly one of the four below. This is the search space that Model B's disk-recovery must resolve against.

03What "rollout" actually is

  • "Rollout" is Codex's own native name for its transcript file — not an agents-cli invention, and not a flag you pass. agents-cli only ever reads files that Codex chose to name rollout-…. discover.ts:1082-1083 · active.ts:364 · watchdog/read.ts:114-115
  • It's always written and required — it's Codex's sole transcript artifact; there is no flag-gated alternative. Each session = one rollout-<iso-ts>-<uuid>.jsonl under a Y/M/D folder.
  • The uuid is in the filename AND inside the file — discovery reads it from the first-line session_meta.payload.id (discover.ts:2537); the sync/watchdog paths parse it out of the filename with a UUID regex (watchdog/read.ts:115).
  • Only the titles file is optional — the sibling ~/.codex/session_index.jsonl (thread titles) is tolerated-if-absent (discover.ts:1026-1027); confirmed missing on workstation while rollouts still exist.
  • Compared to others: it's just Codex's flavor of the same idea — Claude names its file <uuid>.jsonl, Codex names it rollout-…-<uuid>.jsonl. Same JSONL content, different naming/foldering convention chosen by each vendor.

04Why cwd is tracked

We store pid + agent + cwd. The pid and agent are obvious; cwd is the subtle one. cwd is the join key that maps a live PID back to its transcript — because transcripts are addressed by directory, not by PID.

pid → cwd → transcript file → id. cwd is the middle link. active.ts:935 (cwd resolve), :360 → db.ts:988-992 (WHERE cwd=?), :289-291 (Claude project dir)
  • Codex has no other handle. Its rollouts are date-partitioned, not cwd-named, so WHERE agent='codex' AND cwd=? is the only way to find the right file. db.ts:988-992
  • Claude's folder is literally the cwd. claudeProjectDirName(cwd) = cwd with / and . replaced by - → ~/.claude/projects/<slug>. active.ts:289-291
  • Captured twice: at launch (writePidSessionEntry, exec.ts:1367) and, for processes not launched via the CLI, live via lsof -a -p <pid> -d cwd (active.ts:729-746). On Windows there is no lsof, so the launch-time cwd is the only source. exec.ts:1000-1001
  • Without cwd: you can see a PID is alive but can't say which session it is — worst for Codex (no other key) and Windows (no lsof fallback).

05Runtime state — what we detect, and what we don't

The big idea: liveness is a cheap on-demand scan, not a maintained state machine. Every agents sessions --active call recomputes state live (sessions.ts:847) — nothing is persisted. It asks "is this PID alive right now," not "what happened to it."

Two different subsystems, don't conflate
The SQLite sessions.db is a historical transcript index (for search/sort/cost), refreshed by an incremental mtime-diff scan on the listing path (discover.ts:182-210). The live --active state is computed fresh in memory and never written there. The daemon has its own crash-recovery (heartbeat, stale-lock) but does not compute session liveness. daemon.ts:175-184

07What doesn't add up (design calls, not sneaked-in fixes)

  • Attribution quality is uneven by harness. Claude exact; Codex fuzzy (wrong when co-located); the other four get no live id. The one mechanism that makes Claude exact (--session-id) doesn't exist for the rest.
  • Grok is a real hole. It has a type slot, a stub parser, and sync/watchdog hooks — but no discovery scanner, so it's invisible to agents sessions. Adding a scanGrokIncremental case is the fix.
  • Live id recovery is implemented for only two harnesses. findSessionFileForKind branches on claude and codex only; adding a resolver per storage layout (L3 directory-per-session for kimi/grok, L4 SQLite for opencode/antigravity) would move the remaining harnesses out of "unresolved."
  • Crash ≠ clean exit is undetectable. There's no exit-code or clean-shutdown marker anywhere in the runtime path — a killed/crashed/powered-off agent is indistinguishable from a graceful quit; it just vanishes. A durable "last-seen + why-gone" would need a persisted state row, which today's design deliberately avoids.
  • The SessionStart hook would fix the id problem at the source — it's the only way to get an exact id from an agent that mints its own (the agent self-reports it). It's built but unwired/uninstalled; wiring it collapses the id tiers up to Claude's exactness for every hook-supporting harness.
