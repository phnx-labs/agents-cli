The ~100 invisible sessions

You asked to see the change before it altered what you look at every day. It already shipped, so this is the real before/after — measured on your fleet, not a mockup.

Two separate root causes. The first is fixed, shipped, and running on every reachable box. The second I found while verifying the first — it is why --resolve still could not find a session, and it has its own fix in review.

01Cause one — panes folded onto one wrong id

agents sessions --active reported one row per working directory, not one row per agent. Panes it could not identify were dropped at active.ts:1466; the fallback then resolved every remaining pane in a directory to the same newest transcript, and dedupe folded them together. A ×25 badge was never one session with 25 processes — it was ~25 distinct sessions wearing one id.

What that looks like on the machine you sit at, after the upgrade:

  4b1a7f22 claude  pids=1 muqsit
Honest caveat. 41 of those 120 rows still carry no session id. They are now distinct rows instead of dropped or merged under a wrong id — which is the fix working — but a pane not launched under an ag-* tmux session still cannot be named. Closing that is a follow-up, and #1765 never claimed it.

02Cause two — the box holding your session was never dialed

With attribution fixed, agents sessions --resolve 2373284d still could not find the session you asked me to resume — even though its transcript is sitting on yosemite-s1. The sweep picks peers by the cached Tailscale snapshot, and that field is wrong in both directions:

devicelive probecached snapshotsweep did
yosemite-s1reachable (manual)absent skipped it — your session invisible
pinnaclesunreachableonline: true dialed it — false "unreachable"
gpu-boxunreachableonline: true dialed it — false "unreachable"

A device registered via: "manual" never gets a Tailscale peer entry, so its online is permanently undefined — and the filter tested === true. Meanwhile every false "unreachable" is treated as doubt, so --resolve refuses to return a match it has already found. One line caused both.

The fresh probe verdict the fix now reads was already being written to the registry by agents devices — nothing new to collect, it was just never consulted by the sweep. Factory's picker had already learned this same lesson (deviceHealth.ts:47); the CLI sweep had not.
