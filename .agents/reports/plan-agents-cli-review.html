01 What changed from your assumptions

The most useful output of the review: five things you (or I) assumed going in turned out not to be true. Reading these first will make the rest make sense.

Correction 1 — why agents view is slow

We both guessed it was the live per-account usage bars (the S/W/M network calls). Wrong. Those are parallel, cached, and sub-second. The real cost is that agents view re-scans the 230–270 MB Claude binary on every single call (~7.5s of a ~13s run) because a catalog-cache guard refuses to save a failed extraction. Evidence in Cluster A.

Correction 2 — why agents sessions --active is slow (the biggest find)

A --local query — which should touch nothing but this machine — actually fires ~60 real SSH calls (~4.3s) to poll remote teammates that already finished. This is the answer to the filed ticket RUSH-2118, and a major reason your Mac feels slow.

Correction 3 — per-harness rule presets (#7)

You asked us to build them. They already exist: agents rules switch codex@ver --preset name ships today, keyed per harness+version. The real gap is small — they only apply after an explicit switch, not automatically when you run the agent.

Correction 4 — R2 backups & CRDT (#4)

R2 sync exists but is an off-by-default beta that the team already demoted in favour of the live --host query and export/import. "Swap CRDT for object-storage versioning" would actually cause silent data loss on the one case CRDT protects. Your revised call — remove the legacy beta, keep+grow export/import — is the right one.

Correction 5 — benchmarks (#5) already partly exist

There are session benchmarks (bench/sessions-perf.ts, bench-ssh.mjs) and a docs/05-sessions.md. The gap is the distributed (cross-fleet) query path isn't benchmarked, not wired to CI, and results aren't documented.

#1 Speed up agents view PR building

Refresheragents view lists your installed agent CLIs and their accounts/usage. You screenshotted it taking many seconds to print.
Root cause (evidence)Each run re-reads the entire 230–270 MB Claude binary to extract its model list (extractStrings, models.ts:344 — it readFileSyncs the whole file). That result is never cached when the extraction comes back empty (models.ts:996: "only persist a non-empty catalog"). The Claude parser's regexes broke for Claude ≥ 2.1.207, so extraction is empty → nothing is cached → the ~1.85s scan reruns × 4 versions = ~7.5s of a ~13s run. Profiler: that scan is 31% of all CPU time.
Approach chosenCache the empty result too, but with a ~24h TTL (self-heals a transient mid-install failure). Drops the cost from every-call to once-a-day-per-version.
Alternatives considered
  • Only fix the broken regexes — helps Claude today but any future format drift silently reintroduces the 7.5s; doesn't fix the whole class. (Kept as a separate correctness PR.)
  • Add a --fast/--no-models flag — a band-aid; the same scan still slows status, inspect, models, versions.
Caching wins because it fixes every consumer at the source, which is exactly your "pre-compute, don't re-parse" principle.
FYIThe broken regexes also make the model column show a meaningless default — filed as a separate correctness issue, not mixed into the perf PR.

#3 agents sessions --active SSH leak PR building RUSH-2118

Refresheragents sessions --active shows what's running right now; --local is meant to answer for this machine only (it's used at every session start).
Root cause (evidence)For a teammate that runs on another box, status is refreshed by SSHing to that box (teams/agents.ts:1150 → syncRemoteMirror → pullRemoteLogDelta). There's no check to skip teammates that already finished, and --local doesn't stop it. A raw strace counted 60 ssh calls to 30 already-done teammates, ~4.3s.
Approach chosen(1) --local never SSHes — read the remote teammate's last-saved state from disk. (2) Even without --local, don't re-poll a teammate whose status is terminal (completed/failed). Target < 500ms.
Alternatives considered
  • Parallelize the SSH calls — still does pointless work and still loads the remote boxes; masks the bug instead of removing it.
  • Cache remote status with a TTL — helps non-local, but a --local query should make zero network calls by definition.
FYIThis is the single biggest contributor to the "why is zion slow" question, alongside #Cluster-A background timers below.

03 Cluster B — Sync surface cleanup

One theme: retire the old heavy session-sync machinery now that the live --host query and export/import cover the job. You already decided the direction here.

#4 Remove R2/CRDT beta; grow export/import needs a flag decision

RefresherThree ways sessions move between machines exist today: (a) --host — read a peer's sessions live over SSH (the default now); (b) sessions export/import — bundle sessions to carry to a new machine; (c) a background R2 sync that uses a CRDT to merge — an off-by-default beta.
Root cause / state (evidence)The R2/CRDT background sync is gated behind a beta flag, off by default (daemon.ts:588), and was already demoted in favour of (a) and (b) (changelog RUSH-1714). The CRDT (crdt.ts) is a small grow-only-set union that only matters when the same session is resumed on two offline machines — it prevents losing one side's turns. Separately, agents drive (#9) is an even older rsync-based sync.
Approach chosen (your call)Delete agents drive and the R2/CRDT background beta. Keep and enhance export/import: tar.gz bundles, and support R2 (or a remote machine) as an export/import destination for backup/restore.
Alternatives considered
  • Swap CRDT for "object-storage versioning" — rejected: R2 here uses single-writer prefixes and unconditional overwrite, so bucket versioning protects nothing; plain last-write-wins would silently drop a machine's conversation turns.
  • Leave the beta dormant — you rejected this: it's dead weight to carry.

Needs you — one small design choice

Destination syntax for the enhanced export. Preference? agents sessions export --to r2://bucket/path (URI style, extensible to ssh://host) vs. --dest r2 --bucket … (explicit flags). I lean URI-style — one flag, and a remote machine becomes --to ssh://mac-mini:~/backups naturally.

Approach chosenRemove it from help and code; if someone types drive out of habit, print a one-line deprecation pointing to sessions export/import.

#6 Hook & command metrics + friction heuristics ready

RefresherWe recently began recording hook execution time. You asked what else to record — failures, timeouts, medians — and scoped per repo (a git hook is slow on a big repo).
Root cause / gaps (evidence)Only hooks that opt into caching get timed at all — the safety guard hooks (git-guard, rm-guard) record nothing. A timeout kills the process before the timing line is written, so timeouts are invisible. The recorded line has no cwd/session/agent. agents perf computes p50/p99 but not failure rate, timeout rate, or per-project grouping — even though the cwd column already exists, it's never read (perf/db.ts:237).
Approach chosenExtend agents perf: add project grouping (reuse the existing repo-aware project key), add p95 / errorRate / timeoutRate, instrument the guard hooks, and persist a real "timed out" status. Plus 5 cheap friction heuristics (repeated commands, guard-block loops, idle gaps) computed from data we already log — no paying an agent to re-read whole transcripts.
Alternatives considered
  • A new agents insights command — rejected: it would duplicate the perf reader; the concept already lives under perf.
  • Fold into agents activity — rejected: activity is "what agents did" (milestones), a different data source and charter.

#8 Routine metrics + index routine/headless/team sessions ready

RefresherYou wanted metrics for routines (scheduled runs), and for routine/headless/team sessions to show rich previews in agents sessions like interactive ones do.
Root cause / gaps (evidence)Routines do save status/exit/duration to disk, but a local routine fire never emits a perf sample (executeJobDetached, runner.ts:1232, skips the timer the other paths use) and duration is dropped from the JSON output. For indexing: interactive, headless, and team sessions all land in sessions.db already — but routine sessions are archived only for claude/codex/cursor (ROUTINE_TRANSCRIPT_SPECS, runner.ts:88), so a routine on gemini/kimi/grok/etc. leaves zero trace.
Approach chosenWrap the routine fire path with the same createTimer the other paths use (metrics for free), add a per-routine stats rollup, and extend the transcript-archive list to every agent so all routine runs get indexed + previewed.
Alternative consideredA separate routine-metrics store — rejected; reuse the perf warehouse so it shows up in the same place as everything else.

#11 Browser/computer audit + preview surfacing ready

RefresherYou want to know which agent ran a browser/computer task (session id on the device, for later git-blame-style tracking), see "used browser/computer" in the session preview, and record analytics for these commands.
Root cause / gaps (evidence)The command files emit nothing directly; two event types (browser.navigate, browser.screenshot) are declared but never fired. However — good news — every browser/computer invocation already gets a command.start/end event stamped with session + agent + machine automatically (the provenance floor). So identity is already there; what's missing is per-action detail. The preview re-scans the transcript on every render to guess "used browser". There is no analytics.db.
Approach chosenEmit typed per-action events (fill in the two dead types, add computer.action), record perf samples with session/agent, persist usedBrowser/usedComputer on the session row (so the preview reads a field, not a re-scan), and put metrics in the existing perf warehouse.
Alternative consideredA new analytics.db — rejected: the perf warehouse already has session_id/agent/status columns; a second store duplicates it and loses cross-referencing.

#12 Skill/plugin/slash-command usage in sessions ready

RefresherYou want each session to record which skills, plugins, and slash-commands it used (per harness), with provenance (which repo/snapshot the skill came from), and make that queryable — so you can analyse which skills lead to helpful sessions.
Root cause / gaps (evidence)Skill detection exists but only for Claude/Kimi (coincidental tool naming), is computed at display time, and is never saved. Slash-commands are actively stripped as noise. Plugins have zero detection. The Claude transcript's opening line literally lists every available skill/plugin/command — and the parser drops it. No provenance (which repo/commit a skill came from) is captured anywhere, and there's no --skill/--plugin query flag.
Approach chosenCapture the skill/plugin source repo + commit snapshot at resolve time; generalize the extractor across harnesses and capture slash-commands; store usage in a new session_resource_usage table (a session uses many skills, so a table not a column); add --skill/--plugin filters.
Alternative consideredExtra columns on the sessions row — rejected; it's many-to-many, which needs its own table to query cleanly.

05 Cluster D — Standalone fixes

#2 Daemon-down notification ready · needs a Mac to build

RefresherIf the background daemon is down, scheduled routines can't fire. You want the user to still be told — and the "daemon is down" alert must not itself depend on the daemon.
Root cause (evidence)Desktop notifications themselves are daemon-independent (a direct spawn). But the only proactive "routines overdue / daemon down" signal (notifyOverdue) is called only from inside the daemon (daemon.ts:505) — so it can never fire while the daemon is down. That's exactly the self-defeating loop you flagged, confirmed in code.
Approach chosenThe MenubarHelper is a separate always-on service that already knows how to read daemon liveness — but only when you click the menu open. Move that check into its existing 10-second tick and deliver via the daemon-independent notify path.
Alternatives considered
  • A separate cron/launchd watcher — more moving parts than reusing the already-supervised MenubarHelper.
  • Rely on launchd auto-restart — doesn't cover a deliberate stop or a crash loop, and only alerts after the daemon is back.
FYIThis one is Swift (the menu-bar app), so it builds/tests on a Mac — I'll route it to an idle Mac (pinnacles), not this Linux box.

#7 Per-harness rule presets — make them apply at run time ready

RefresherYou want different rule sets per harness (Codex vs Claude have different "personalities"), compiled and activated when you run that harness.
Root cause / state (evidence)This already exists — agents rules switch codex@ver --preset name stores a preset per harness+version (state.ts:1153). The gaps: only one preset is actually defined, and a preset only takes effect after an explicit switch — agents run doesn't re-apply it (exec.ts never recompiles rules at launch).
Approach chosenMake agents run <harness> apply the active preset at launch (mirror the existing project-rules "compile at shim launch" path, with a fast skip-cache so it costs ~0ms when nothing changed), and author a couple of real example presets.
Alternative consideredBuilding a preset system from scratch — unnecessary; it exists and works, it just doesn't auto-apply.

Needs you — scope

Per-model presets (different rules for Opus vs Sonnet) are a small extra (a model-keyed field + a --model flag). Ship version-level now and model-level as a fast follow, or do both together?
