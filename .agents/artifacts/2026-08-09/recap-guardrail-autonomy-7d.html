The through-line is the same as always: more autonomy, but only where it stays safe. What changed this week is that a lot of the machinery meant to enforce that was quietly not working — and the fixes are specific.

Findings

The Stop gate was refusing every macOS session — because of one quote character

The failure. The keep-moving Stop gate (the hook that stops an agent from quitting with work half-done) had a Python regex embedded in a shell heredoc, and the regex character class contained a literal single-quote: [)\]\'\"]. On Linux that parses fine. On macOS it does not — every Mac's /bin/bash is bash 3.2, and bash 3.2 mistracks a lone quote inside a heredoc nested in a $(...) substitution. The whole script became unparseable: unexpected EOF while looking for matching ')'.

Here's the trap: an unparseable hook still runs, and bash exits 2 on a syntax error — and 2 is the exact code the harness reads as "block." So every Stop on every macOS Claude session was mechanically refused, whether or not the work was actually done. No Mac session could end. It passed CI because CI runs on Linux bash 5, which parses the identical file without complaint.

The fix. The two quote characters were replaced with hex escapes — [)\]\x27\x22] — so the heredoc body carries no literal quote at all. More importantly, a new syntax_test.sh now runs bash -n against both the system /bin/bash and the PATH bash on every shell hook, so a bash-3.2-only parse failure can never ship green off a Linux CI again.

Now. The gate parses everywhere, and — a side effect worth noting — the task-aware logic it was supposed to run had been dead-on-arrival too (its 8 tests had been red since it landed, because the script never parsed). Fixing the quote turned the feature on for the first time.

commits: ecb9574 (the fix), 2615e49 (the feature it un-bricked). Read: git show ecb9574.

Denials now tell the agent what to do instead — so it stops retrying the wall

The failure. When a guard blocked a dangerous command, it printed one line: the reason. Nothing else. So the model saw "denied," had no encoded next step, and did the only thing it could — retried the identical blocked command. The measured damage: one session hit the rm.protected-path guard 87 times; another hit git.reset 43 times. Each retry a wasted turn and wasted quota, looping against a wall that was never going to move.

The fix. Every denial across git-guard, rm-guard, and large-file-add-guard now emits a structured three-line contract instead of a bare reason:

blocked_op: git.reset
reason: git reset is denied (rewrites history or destroys work).
do_this_instead: reconcile with `git rebase origin/<default>` (or `git pull
  --rebase`); never `reset --hard`. Commit instead of stashing; resolve
  obstacles at the source.

Now. The next model turn has the safe alternative sitting in context. The retry loop breaks because the agent is handed the exit, not just the wall.

commits: a934dd8 (RUSH-2295). Read: git show a934dd8.

Four guards had been silently dead for up to 82 days

The failure. A hook needs two things to fire: the script, and a hooks: entry registering it in agents.yaml. Only the script side was ever tested. So when two unrelated commits — one titled "fix pre-commit validator," one titled "remove legacy hook config" — deleted registration lines as collateral, nothing failed loudly. Each orphaned script kept passing its own isolated test while never firing on a live event. The casualties:

  • expand-promptcuts and expand-bang-commands (your #shortcut and `!cmd` prompt expansions) — dead since May 13.
  • linear-tasks (the sprint board injected at session start) — dead.
  • large-file-add-guard (blocks committing files over 5 MiB — a data-loss guard) — silently off from June 24 to August 3.

The fix. All four re-registered (agents.yaml went from 13 hooks to 17). And the real gap — no test for "am I registered" — is closed: a new registration_test.sh walks every hook script and fails unless each one is either registered, invoked by a registered script, or explicitly allowlisted. It was validated by replaying the exact historical drop and confirming it fails on precisely the three scripts that vanished — so it can't pass only against the fixed state.

Now. A future commit that drops a registration under an innocent-looking subject fails the pre-PR gate instead of shipping a dead guard nobody notices for months.

commits: 14b3aa2 (re-register), 4cdfc40 (the integrity test, RUSH-2119). Read: git show 4cdfc40.

The Stop gate stopped looping — and learned to read the checklist

The failure. A fleet audit over ~6 days / 1,594 sessions found the open-PR Stop gate fired 434 times across 82 sessions — 22 sessions looping ≥10×, 7 looping ≥20×, one burning through its usage limit mid-loop. The gate had no memory of how often it had already fired, so a session correctly waiting on a background CI watch got re-blocked by the identical "keep driving" text on every single Stop.

The fix — three moves:

  • Stateful de-escalation. The gate now counts its own prior fires this session (it scans the transcript for the harness's re-injected feedback marker). On the 3rd+ fire on the same item it stops repeating itself and instead surfaces real exits — name the watcher and stop, escalate out-of-band, or set a wakeup and stop.
  • Task-aware. A new todo-progress.py folds every checklist-shaped call — TaskCreate/TaskUpdate and TodoWrite/update_plan — into one count of remaining items. If the agent tries to stop with items still open and no valid reason, it's blocked and told which item to advance next, by name.
  • Evidence-gated, not phrase-gated. "The background watcher owns this" is only accepted if the transcript actually contains a real backgrounded watch or a ScheduleWakeup/Monitor call — prose alone no longer clears the gate.

And one sharp correction (RUSH-2394). Backgrounding gh pr checks --watch was briefly accepted as that evidence — but for a headless agent that watch is a child of its own process tree, so it dies the instant the agent exits, stranding the PR (seen on real PRs #2334 and #2352). The gate now rejects it and points at agents pr land --detach, a lander that runs in its own process group and outlives the session.

Now. An agent can't quit with a checklist half-done or a PR stranded — but a session genuinely blocked or genuinely waiting isn't punished into a quota-burning loop either.

commits: 194f62a (de-loop), 2615e49 (task-aware, RUSH-2113), dfa0164 (reject fragile watch, RUSH-2394), 7703e22 (recap before self-exit). Read: git show 194f62a.

Guards that refuse the two git moves you can't undo

The failure — remote branch deletion. git-guard blocked the local git branch -d, but not the remote form. An agent could run git push origin --delete <branch> (or the colon-refspec :branch) and it went straight through. If that branch held commits nobody had pulled — a colleague's in-flight work, or the agent's own unmerged branch — those commits become unreachable. Real, hard-to-recover loss.

The failure — stale worktree base. main-branch-guard checked the shape of a worktree base (is it an origin/* ref?) but never its freshness. An agent that hadn't fetched could branch off a week-old origin/main, build on top of code a newer merge had already superseded, and only discover it at merge time — or worse, open a "fix" that silently reverts someone's newer work.

The fix. Remote deletion (push --delete / -d / :refspec) is now denied, while gh pr merge --delete-branch — cleanup of an already-merged branch, which loses nothing — stays allowed. And a worktree base that resolves to an origin/* ref untouched by a fetch in the last 15 minutes (AGENTS_WORKTREE_FETCH_MAX_AGE_SEC, default 900s) is rejected with "run git fetch origin first."

Now. The dangerous forms fail closed with a named alternative; the safe forms stay frictionless. Autonomy stops exactly at irreversible loss.

commits: fce3365 (remote delete), cbf1a28 (stale base). Read: git show fce3365.

Unattended work has to prove it happened — exit 0 is not evidence

The failure. The single most common failure of an agent running with nobody watching is a silent success: it hits a wall, explains the wall politely, and exits 0 — which the dispatcher counts as done. A whole rule now catalogs seven of these, each observed:

What reported success What was actually true
dispatch exit 0 the agent never got a shell (sandbox died); zero work done
agents notify → ok:true nothing delivered — credential unreadable headless
dispatch record "status": "running" process long dead, box idle
capability probe passed it exercised a different operation class than the job
a result file read as current it was the previous run's leftover output
routines add accepted the YAML it silently dropped the devices: pin
ticket queries "working" shared API quota exhausted fleet-wide

The fix. New unattended-verification rule: never treat process success as task success. Close every unattended unit of work by asserting a postcondition you can mechanically check — opened a PR? query it. Merged? confirm it's on origin/<default>. Sent a message? confirm the send says delivered, not that the CLI returned. A companion rule adds current-code anchoring: before diagnosing a bug or opening a fix, git fetch and git rev-list --count HEAD..origin/<default> — because a real incident had an agent diagnose against a checkout 39 commits stale and open a "fix" that reverted a deliberate newer change. The fix was the regression.

Now. A dispatched agent is instructed to check the artifact, not the exit code, and to say "unverified" with the named gap when it can't — instead of rounding a polite wall up to "done."

commits: 25fe42f (assert outcomes), 10d9d30 (current-code anchoring). Read: git show 25fe42f.

The same guards now actually fire on every harness and OS

The failure. Every guard read Claude's payload shape only — tool_input.command, snake_case. Grok sends camelCase (toolInput.command) and names its shell tool run_terminal_command, not Bash. So on Grok a guard found no command, assumed there was nothing to check, and waved every git command through — a fail-open guard is worse than no guard, because it looks present. Separately, Windows hooks hardcoded python3, which on Windows is often the Microsoft Store stub that does nothing, and a timed-out command was killed without its child tree.

The fix. Guards now read both field conventions and a wider shell-tool set before concluding there's nothing to inspect. Windows prompt hooks select py -3 (the real launcher) and fall back to a clean no-op if no interpreter works. Timed-out Windows commands are killed with taskkill /T /F — the whole tree, not just the parent.

Now. A git command on Grok is actually inspected; Windows prompt-expansion runs against a real interpreter and leaves no orphaned processes.

commits: efc7fef (camel/snake stdin), 9c2f7d4 (Windows launcher), dde472b (tree-kill). Read: git show efc7fef.

The daemon's hidden timers became real, pinnable routines

The failure. Eight housekeeping jobs — watchdog, device-probe, tmux-reconcile, launch-health, fleet-cache-warm, session-cache-warm, usage-refresh, auto-dispatch — lived as hardcoded setInterval timers inside the daemon binary: a second, unowned scheduler you couldn't list, pause, or pin. The sharp edge was auto-dispatch: as a hardcoded tick it couldn't be pinned to one box, so every daemon on the fleet independently polled the same shared Linear queue with no coordination — the same ticket dispatched N times.

The fix. All eight ship as declarative command:-mode routines invoking agents __daemon-tick <name> on their old cadences — now listable (agents routines list), individually pausable, and device-pinnable. auto-dispatch can be pinned to a single box so the fleet stops double-firing.

Now. The daemon's background work is visible and controllable like any routine, and the multi-box Linear stampede has an off switch.

commits: 29c2c18 (RUSH-2353). Read: git show 29c2c18.

Sessions resume and exit themselves — safely

The failure. Continue/restore/recover logic lived only as slash-command bodies, so a harness that supports skills but not commands got nothing. And /done's self-exit inlined a raw kill -TERM $PPID, which the auto-mode permission classifier blocked in dispatched runs — so a headless session literally could not terminate itself cleanly.

The fix. A sessions plugin moves the logic into skills (continue / insights / restore), reachable by nearly every harness, with the commands as thin aliases. And /self:close is a proper guarded primitive: a read-only ps check first refuses to signal an infra parent (sshd/tmux/init), then sends SIGTERM only — and the permission is allowlisted as the exact string Bash(kill -TERM $PPID), never a general kill allow. It can't target another pid, can't escalate to SIGKILL, and lets the harness flush its transcript before exiting.

Now. A crashed or dispatched session can be resumed by any harness, and a headless agent can end itself cleanly without a stuck permission prompt — without opening the door to killing the wrong process.

commits: fd4d352 (sessions plugin), a677cc5 (/self:close). Read: git show a677cc5.

Evidence

Every fix above lands at one of five points in an agent's unattended lifecycle. Read left to right: context is injected, the agent works, PreToolUse guards refuse irreversible actions, the Stop gate refuses a false or looping finish, then the session clears to a clean self-exit.

Recommendations

Nothing here needs you — it's a report. But the pattern points somewhere: the eight housekeeping routines now run, yet the daemon still emits nothing into the unified event stream (RUSH-2439). So an unattended run's progress is a private log silo, not a signal the fleet can see — the same "silent success" shape this whole week was about, one layer up. That's the next wall worth building.
