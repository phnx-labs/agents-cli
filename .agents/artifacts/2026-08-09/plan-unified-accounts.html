Unify accounts across native logins and provider credentials

agents-cli currently has two account-like systems: discovered native harness logins and provider-wide keys embedded in custom harness profiles. This plan makes Account the single named credential identity, keeps Harness as execution configuration, and makes Provider non-secret connection metadata.

Native labels currently store agent + SHA-256 identity fingerprint, never version membership·Provider-backed profiles currently share one keychain item per provider·agents view renders provider email/account identity but does not resolve logical account labels·Target model: Provider describes access; Account owns identity and secret reference; Harness consumes an Account

Purpose

What the user should experience

When a user names claude@2.1.220 as work, every surface that shows that same Claude identity should display work; the label should not disappear in agents view. When the user adds an OpenRouter key as openrouter-work, any compatible custom harness should reference that account by name instead of owning a hidden copy of provider auth. A harness continues to answer how to run; an account answers whose authorization to use.

The user should be able to answer three questions without knowing where credentials happen to live:

  1. agents accounts — what identities can I run as, how are they authenticated, and where are they available?
  2. agents harness view deepseek — which host, model, endpoint, and account does this harness use?
  3. agents run deepseek --account openrouter-personal — can I deliberately override the configured account without falling back to another identity?
Design rule: an Account is a named authorization identity. OAuth sessions, setup tokens, bearer tokens, and API keys are credential methods of that identity; they are not separate top-level concepts.

Why the current behavior feels inconsistent

Current concept Storage and binding User-visible consequence
Native account label ~/.agents/accounts.yaml stores {agent, fingerprint}; matching versions are discovered live Correctly survives version changes, but agents view shows only provider email/account id, not the logical label
Provider auth in a custom harness Profile YAML stores provider and keychain item; keychain item is provider-wide One OpenRouter key is silently shared by every OpenRouter harness; two OpenRouter accounts cannot be named distinctly
Custom harness Profile combines host, model, endpoint, provider, and auth binding Execution configuration and credential identity are fused; --from-secrets copies credential material into profile-owned auth
Provider Mostly a display label and keychain namespace No canonical provider contract tells hosts how to inject or validate an account

Proposed Changes

The target model

Use three nouns with non-overlapping ownership:

  • Provider — non-secret protocol metadata: provider id, display name, default endpoint, supported credential methods, optional identity/health probe, and host-specific injection adapters.
  • Account — a stable local name and id for one authorization identity at one provider. It owns the credential method and a secret selector or native-home matcher, but never raw secret material.
  • Harness — an executable configuration: host CLI, optional host version, model catalog, endpoint override, and a default account reference.

At runtime the resolver derives an Attachment: one account is usable through one local harness/version/credential location. Attachments are observations, not durable user configuration. Persisting them would recreate the version binding the current fingerprint design correctly avoids.

Account schema

The account registry uses a stable generated id so rotating a key or refreshing OAuth does not rename the identity. The selector is a discriminated union; raw credential values never appear here.

# ~/.agents/accounts.yaml — metadata only, safe to sync
accounts:
  - id: acct_01J...
    name: work
    provider: anthropic
    credential:
      kind: managed-login
      harness: claude
      identityFingerprint: 8fd9...

  - id: acct_01K...
    name: openrouter-work
    provider: openrouter
    credential:
      kind: api-key
      secretRef: account/acct_01K...
    displayIdentity: "Production API Key"

Credential kinds are behavior, not separate registries:

Kind Secret owner Matching / availability Rotation behavior
managed-login Native harness version home Match provider identity fingerprint discovered from each installed home Harness refreshes its own OAuth/session tokens; account id/name remain stable
oauth Account secret backend Provider adapter owns refreshable token set and scopes Refresh replaces secret payload, never account metadata
api-key Account secret backend Presence plus optional provider identity/health probe Replace secret under the same account id
bearer-token Account secret backend Presence plus optional expiry/scopes metadata Replace or re-authenticate under the same account id

Do not hash an API key and use that hash as the account's primary identity: rotating the key would create a different account. A credential fingerprint may be recorded only as non-secret diagnostic metadata for duplicate detection.

Resolution contract

  1. Resolve the requested harness and its default account; an explicit --account wins.
  2. Verify the account provider is compatible with the harness/provider adapter.
  3. Resolve availability on the execution device:
    • managed-login: choose a healthy installed host version whose live identity fingerprint matches.
    • secret-backed: read the account's local secret reference and run the provider health probe when available.
  4. Build the host-specific env/arguments from the provider adapter.
  5. Spawn exactly one identity. Missing, incompatible, or unhealthy accounts fail with a named reason. There is no identity fallback.

This preserves the existing fail-closed guarantee of run --account and extends it to custom harnesses and remote dispatch.

Migration sequence

  1. Read old labels: entries and assign stable account ids while retaining the same fingerprints and names.
  2. For each profile with auth.keychainItem, group by exact keychain reference, create one explicit account per unique reference, and point consuming profiles at it.
  3. Use a deterministic collision-safe name such as openrouter for one credential or openrouter-2 only when distinct credential references exist; never infer two accounts from two models.
  4. Write the new metadata atomically only after every profile reference resolves.
  5. Leave raw credential bytes in their existing secret backend during metadata migration; moving bytes is a separate verified step with rollback-safe copy-then-delete behavior.
  6. After successful verification, remove profile-owned auth fields and provider-wide ownership code. Do not keep dual read paths.

Delta Spec

ACC-1 — One named authorization identity

An account MUST have a stable generated id, a unique local name, one provider, and one credential method. Rotating or refreshing credentials MUST NOT change the account id or name.

ACC-2 — Secrets stay out of metadata

Account metadata MUST contain only selectors, fingerprints, safe display metadata, and secret references. Raw access tokens, refresh tokens, setup tokens, bearer tokens, API keys, emails derived from private auth payloads, and provider account ids MUST remain in the owning secret backend or harness home.

ACC-3 — Version membership is derived

A managed-login account MUST match installed versions from their live provider identity. Version numbers and devices MUST NOT be persisted as account membership.

ACC-4 — Harnesses consume accounts

A custom harness MUST reference an account rather than own credential material or a provider-wide keychain item. Model and endpoint configuration remain harness-owned. Provider compatibility MUST be checked when the harness is written and again when it runs.

ACC-5 — One resolver, every boundary

Native runs, custom harness runs, local teams, remote teams, --host dispatch, routines, and run failover MUST resolve accounts through the same contract. The target execution device owns availability resolution.

ACC-6 — Fail closed

An explicitly requested or harness-default account that is missing, unhealthy, incompatible, or unavailable MUST fail with the account and device named. It MUST NOT select another identity, provider credential, native version, or host-managed login.

ACC-7 — Labels render consistently

Every account-aware human surface MUST prefer accountName · providerIdentity when both exist. Machine output MUST expose stable accountId, accountName, provider, credentialKind, and availability separately; consumers MUST NOT parse the display string.

ACC-8 — Provider is metadata, not identity

A provider entry MUST describe supported authentication and injection behavior without storing user credentials. Multiple accounts MAY reference one provider, and multiple harnesses MAY reference one account.

Risks

Risk Mitigation
An API key may represent a project, workspace, service account, or human rather than an email identity Account is defined as authorization identity, not person; safe provider metadata is optional
Provider-wide keychain naming currently collapses multiple accounts Account id namespaces the secret reference; migration groups only identical existing keychain refs
A provider credential can be compatible with several host protocols Provider adapters own injection mappings; harness profiles never hardcode auth env ownership
Host-managed providers such as OpenCode hide their own internal account model Represent them as managed-login when stable identity inspection exists; otherwise report availability as unverified and do not merge identities
OAuth refresh and API-key rotation have different lifecycles Credential discriminated union gives each adapter explicit refresh/rotation behavior under one account id
Metadata sync can reach a device before its secret Availability is device-local and fail-closed; list surfaces show missing on <device>
Migration could delete the only working credential Metadata first, verify resolution, then copy-then-delete secret bytes; no dual runtime paths remain afterward
Existing automation uses --auth-provider / profile login commands Generate command-index usage inventory, migrate docs/system consumers, and land the cutover in one release with explicit errors naming replacement commands

Research and Verification

Current-code evidence

  • account-labels.ts stores {agent, fingerprint} and discovers matching versions live; the account label is not version-bound.
  • view.ts delegates identity rendering to accountDisplayLabel, which shows email / provider account id and never reads the account registry; this is why work is absent.
  • profiles.ts binds auth.envVar and a provider-derived keychain item directly into each profile, while preset profiles deliberately share that item across the provider.
  • resolveProfileEnv reads the keychain token at spawn time, which is the correct secret boundary to preserve behind the new account resolver.

External constraints

  • OAuth 2.0 security practice treats access/refresh token handling as a lifecycle distinct from static API keys; the account model therefore abstracts credential method rather than flattening all secret payloads into one field. Source: IETF OAuth 2.0 Security Best Current Practice, RFC 9700.
  • OpenRouter currently distinguishes completion API keys from management keys and exposes safe key metadata such as name, hash, limits, and expiry. A provider account cannot be modeled as only an email address. Sources: OpenRouter authentication methods, OpenRouter key metadata.

Independent review

Two blind read-only reviewers independently converged on the same boundaries:

  • The native reviewer found that --from claude@2.1.220 already binds work to the Claude account fingerprint and discovers all matching versions. It identified the missing agents view lookup and the same missing lookup in the interactive account picker.
  • The provider reviewer found that profile auth combines execution topology with credential ownership and that ${provider}.token collapses every OpenRouter harness onto one credential. It independently recommended Harness = host + endpoint + model + accountId and device-local secret availability.
  • Both reviewers separated durable Account metadata from derived local attachments, required target-device resolution for remote runs, and rejected email as the universal account identity.

One divergence was migration policy. A reviewer proposed retaining legacy profile auth as a compatibility read for one release. This plan rejects that dual runtime path because repo policy forbids compatibility shims: migration is atomic, verified before old fields are removed, and failures stop with the original data intact.

Tracking

  • RUSH-2402 — Unify native and provider credentials under one account model
  • Related narrower work: RUSH-2400 (Cursor multi-account isolation) and RUSH-2401 (agents view account counts). RUSH-2402 owns the cross-harness model; those tickets should implement against this contract rather than create parallel account semantics.
Decision for implementation: keep the three nouns separate. Provider describes access, Account names authorization, Harness defines execution. The label attaches to the provider identity, not to one installed version and not to an email string.
