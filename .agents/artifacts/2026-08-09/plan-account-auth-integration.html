Fold the Claude setup-token into agents accounts, and never sync it to the interactive host

The interactive/headless split (shipped 1.22.34) fixed the revocation, but the headless setup-token is an email-keyed secrets bundle bolted beside `agents accounts`, with no fleet sync and no interactive-host protection. Make the account the unit: mint a per-account setup-token, surface it in `agents accounts`, and auto-sync it to worker devices only — the interactive host always stays on its rotating OAuth login.

Purpose

Two gaps remain after the interactive/headless auth split:

  1. The setup-token leg is bolted beside agents accounts, not through it. agents accounts (account-labels.ts) names an identity by {agent, fingerprint} and holds no credential. The headless setup-token lives in a separate auth secrets bundle keyed by email (claude-account-token.ts:58). The two only connect indirectly, so there is no single "account" object that knows both its interactive login and its headless token.
  2. No fleet sync, and no protection for the interactive host. Auto-sync of the auth bundle (RUSH-2371) does not exist; portability is manual agents secrets export auth --host. Nothing excludes the interactive box — so a future naive sync could place a worker credential on the one machine that must always run the rotating OAuth login.

The intended outcome: an account is the unit that owns both credentials — the rotating interactive login (stays in its version home, never copied) and an optional non-rotating setup-token (mintable, portable to workers). Sync distributes the setup-token to worker devices and never to config.interactiveHost.

Proposed Changes

1. Key the setup-token to the account, not the raw email — claude-account-token.ts. Today claudeAccountTokenKey(email) derives CLAUDE_CODE_OAUTH_TOKEN_<EMAIL_SLUG>. Add an account-fingerprint-addressed lookup so resolveClaudeSetupToken(home) resolves the token via the home's discovered account identity (the same identityFingerprint(agent, accountKey) used by account-labels.ts:16), falling back to the email key for already-provisioned tokens. One canonical address per account, no drift.

2. Surface the token on the account — account-labels.ts / commands/accounts.ts. Extend DiscoveredAccount (the derived, non-persisted shape at account-labels.ts:13) with headlessToken: boolean (is a setup-token provisioned for this account's fingerprint). Render it in agents accounts / --json. accounts.yaml stays fingerprint-only — the token stays in the auth bundle, only its presence is surfaced.

3. Account-scoped mint command (RUSH-2364) — commands/accounts.ts. Add agents accounts mint <label> (thin wrapper over the fleet:mint-auth recipe): drive claude setup-token, store the result in the auth bundle under the account's canonical key. Replaces the manual recipe with one command bound to a named account.

4. Auto-sync to workers, excluding the interactive host (RUSH-2371) — new sync path. Distribute the auth bundle's per-account setup-tokens to worker devices. Target set MUST exclude config.interactiveHost, mirroring apply.ts:236: Object.values(registry).filter(d => !isControlDevice(d) && d.name !== interactiveHost). The interactive box is never a sync target — it always runs its own OAuth login.

5. Credential-class boundary in the spec — docs/specifications.md. Record that EXEC-ACCOUNT-1 ("raw tokens stay in the version home, never copied") governs the rotating login; the non-rotating user:inference setup-token is a distinct, explicitly-portable class an account may carry and sync. Keeps the integration legal, not a silent violation.

Public Interface

agents accounts                     # now shows a per-account "headless token: yes/no" column
agents accounts mint <label>        # NEW — mint + store a setup-token for a named account
agents accounts sync                # NEW — push per-account setup-tokens to WORKERS only
                                    #        (config.interactiveHost is always excluded)

No change to agents run, the interactive/headless split, or agents run --account (which already selects a version by live identity, fail-closed).

Risks

Risk Mitigation
Bending EXEC-ACCOUNT-1 (accounts never copy credentials) Explicit credential-class split in the spec: rotating login never copied; non-rotating setup-token is a distinct portable class.
Re-keying breaks already-provisioned email-keyed tokens resolveClaudeSetupToken falls back to the email key; no forced migration.
Sync places a token on the wrong box interactiveHost exclusion is unit-tested; sync is worker-only by construction.
Usage bars still "pending" Out of scope — an external Anthropic scope limit (RUSH-2392), not solvable here.
