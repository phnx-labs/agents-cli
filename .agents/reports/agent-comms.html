How agents reach each other:
feed, mailbox, session-inject

Three mechanisms that look similar and aren't. The feed is a bulletin board you pull. The mailbox is private mail dropped into a running agent. Inject types an answer into a parked agent's live terminal. agents message is a router that picks between the last two by the recipient's state — the feed sits outside it entirely.

01The router: delivery is chosen by agent state

These aren't three tools you choose between. agents message inspects the recipient and routes — the precedence lives in lib/answer-router.ts · resolveAnswerRoute. The feed is not in this tree; it's a board, not a delivery.

03Feed — a board, with two very different lanes

One command, two stores that behave oppositely. This split is the crux of the whole question, so it gets its own diagram.

  • Open blocks — .history/feed/<blockId>.json. Last-writer-wins state ("this agent needs you"), with a full answer / park / receipt lifecycle. The primary content of agents feed. On read it SSH fan-outs to every registered device (commands/feed.ts runs agents feed --json on each peer) — fleet-wide, no auth beyond fleet SSH.
  • Status posts — .history/activity/<sessionId>.jsonl. Append-only events. agents feed post "text" writes one as tier:'milestone', event:'status.posted' (lib/feed-post.ts). Shown in the recent-activity lane at the bottom of agents feed — but read local-only. The fan-out carries blocks, not the activity lane.

04Mailbox — private mail for a running agent

A file spool, one box per logical agent, drained at the recipient's next tool call.

  • Store: .history/mailbox/<mailboxId>/{inbox,processing,consumed}/<msgId>.json. mailboxId = teams agentId ?? sessionId — one box, one consumer.
  • Anti-misroute: "a message can never reach the wrong agent." The to field is stamped into the JSON and validated on consume; a mismatched or corrupt file is archived, never delivered.
  • Consumption: not passively pushed — the mailbox-inject PreToolUse hook drains the inbox at the next tool call. The agent must be running (reaching a tool call); it does not need a terminal. At-least-once via inbox → processing → consumed, dedup by msgId.
  • Cross-machine: the spool is local; --host re-execs the whole agents message over SSH so the box is written on the host that owns the agent. No shared relay.

05Session-inject — keystrokes into a parked agent

When an agent is blocked on a question, there's no next tool call to drain a mailbox. Inject types the answer straight into its live terminal.

  • Mechanism: tmux send-keys, iTerm osascript … write text (focus-safe, no activate), VSCodium --open-url …/inject, or pty write. Ink-TUI safe: text and Enter are two separate writes.
  • Requires: parked on a question and an addressable rail. Only tmux rails are addressable by session id; no rail → "no addressable reply rail … relaunch under a tmux/pty rail to inject."
  • Locality — not strictly local: tmux/iterm/vscodium inject into a remote session over SSH via --host; only the pty backend is hard local-only. Session-id lookup reads local state (needs sync). Ghostty is coarse (steals focus) and refused unless explicitly opted in.
  • Headless with no rail → can't inject. Falls back to agents run --resume (route ② above).

06The gap that blocks the goal

The reason to make agents post status is passive observability — so you don't have to poll each box to know what a headless run is doing. Two findings stand in the way today.

the gap Status posts don't travel. feed post writes to the local-only activity lane, and the feed's SSH fan-out carries only open-blocks. A status posted by a headless agent on yosemite-m3 is not visible when you run agents feed on zion. Instructing agents to post is necessary but not sufficient — the activity lane also needs fleet fan-out (or posts routed to a fleet-visible surface) for the goal to work.
